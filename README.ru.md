# LLMCrew DailyBench

Детерминированный бенчмарк для **локальных** языковых моделей с оценкой по
наблюдаемым результатам. Бюджет — 16 ГиБ VRAM, поэтому внутри репозитория сьют
называется *DailyBench-16*.

Десять балльных категорий, 47 заданий, 100 баллов — плюс два **визуальных
блока** (20 сценариев симуляций на Three.js и 1 свободная арт-работа), которые измеряются в
headless-браузере и показываются вне общего счёта. Каждый балл берётся из проверяемого результата — разобранного
ответа, файла на диске, прогона скрытых тестов, журнала вызовов инструментов,
отрисованного кадра — и никогда из вердикта модели-судьи. Сьют целиком
порождается из одного seed'а: два прогона двух квантизаций получают
побайтово одинаковые задания.

```
make setup                       # .venv + pytest (uv)
make agent                       # pi — агентный рантайм категорий C/K/L
make selfcheck                   # без GPU: генераторы и evaluator'ы должны сойтись
python -m dailybench bench --config qwen3.8-27b-ud-q3-k-xl --speed
python -m dailybench report runs/qwen3.8-27b-ud-q3-k-xl runs/qwen3.8-27b-ud-iq3-s
```

## Что сравнивает лидерборд

Одна строка — одна *конфигурация* (модель + квант + рантайм + тип KV-кэша +
окно контекста), а не имя модели: одни и те же веса в `Q3_K_XL` и `IQ2_S` — это
разные результаты. В отчёте видно, что именно измерено, на какой GPU, какой
командой запуска и с какой SHA-256 файла весов.

Качество и скорость не смешиваются: качество — сумма баллов, скорость —
отдельный профиль (TTFT, скорость префилла и генерации, пиковая VRAM на
заполненном контексте). Конфигурация, которая не помещается в бюджет или не
прошла допуск по длинному контексту, так и помечается: непроверенное никогда не
превращается в ноль баллов.

## Категории

| Ключ | Категория | Баллы | Заданий | Что именно проверяется |
|---|---|---:|---:|---|
| A | Следование инструкциям | 10 | 5 | Формат вывода, точное содержимое и порядок — разбором ответа |
| B | Рассуждения | 15 | 15 | Одно точное значение на задание (числа, дроби, порядки, длительность) |
| C | Код | 20 | 3 | Собирает агент в рабочей копии; решают скрытые тесты: патч Python-репозитория, конкурентность Go, результат SQL |
| D | Вызов инструментов | 14 | 7 | Журнал вызовов, состояние файлов после прогона, отсутствие разрушений |
| E | Длинный контекст | 10 | 5 | Одно значение из документа на 8K–28K токенов, допуск измеряется |
| F | Устойчивость к галлюцинациям | 8 | 1 | 10 вопросов: 5 с ответом, 5 без — каждая выдумка снимает баллы своего вопроса |
| G | Структурированный вывод | 8 | 4 | Соответствие JSON Schema (типы, enum'ы, границы, лишние ключи) |
| H | Многоходовый диалог | 6 | 3 | Исправление по ходу диалога и сохранение ранних ограничений |
| I | Работа с файлами | 4 | 2 | Агрегация и разрешение противоречий по набору файлов |
| J | Ревью кода | 5 | 2 | Занесённый дефект локализован, а исправление проходит скрытые тесты |

Внутри отчёта каждая категория нормируется в 0–100 %, итог — сумма заработанных
баллов (максимум 100).

## Лимит ответа: окно, а не лабораторный потолок

Ответ не ограничивается отдельным бюджетом: лимит = окно модели минус промпт
(`unbounded_budget`). Если модель потратила 100 КБ на размышления и не дошла до
текста — это её результат, а не наш потолок, и расход документируется
обязательными полями (`spend` в каждом транскрипте: токены ответа, токены
размышлений, секунды, TTFT, скорость). `reasoning_effort` не форсируется — стенд
отдаёт свой дефолт, и это часть провенанса. Старый режим с таблицей бюджетов
остаётся: `unbounded_budget = False`.

## Артефакты собирает агент, а не диктовка в чат

Три категории, которые производят *файл* (C — код, K/L — визуальные страницы),
решает не один промпт с разбором ответа, а кодинг-агент
[`pi`](https://pi.dev) в копии репозитория задачи: он читает файлы, правит их,
запускает собственные тесты проекта, и **оценка идёт по тому, что осталось на
диске** — модель, которая «ответила верно», но файл не записала, работу не
закончила.

Чат-путь остаётся для нарративных категорий (A, B, D, E, F, G, H, I, J) — там
честная форма задачи именно такая, — и доступен для C/K/L флагом `--no-agent`,
так что два каркаса можно сравнить на одном сьюте.

Инварианты каркаса (одинаковые для всех моделей, проверяются тестами):

- **пришпиленный агент**: `pi 1.0.0`, инструменты `read,bash,edit,write`;
- **изоляция от машины**: `--no-session` (никакого состояния между заданиями),
  `--no-context-files` (свой `AGENTS.md` репозитория не должен вписываться в
  промпт), `--no-extensions --no-skills --no-prompt-templates` (`.pi/`, который
  создаст модель, не меняет каркас), `--offline` (без обновления каталога и
  телеметрии), `--no-approve`;
- **один endpoint, один ключ**: одноразовый `PI_CODING_AGENT_DIR` со
  сгенерированным `models.json` — только endpoint прогона, политика
  `temperature=0`/`top_p=1` и потолок ответа категории;
- **никаких подсказок**: рабочая копия содержит ровно фикстуру (плюс
  пришпиленный `vendor/three.js` для K/L); `AGENTS.md` агента сообщает только,
  где библиотека и какой файл оценивается;
- **toolchain доступен агенту**: `PATH` дополняется Go SDK, который бенчмарк
  находит сам, — агент не может быть измерен на худшей информации, чем
  evaluator;
- **отчёт агента — это провенанс**: поток JSON-событий → вызовы инструментов,
  ходы, расход токенов; упавший агент сохраняет события и хвост stderr вместо
  того, чтобы быть оценённым как пустой каталог.
- **пустой stdin**: `pi` читает stdin, если это пайп, и ждёт EOF, поэтому запуск
  идёт с `DEVNULL` — иначе прогон из шелл-пайпа висит весь wall clock без единого
  события;
- **потолок ответа — оконный бюджет**, а не чат-таблица: агент тратит его на
  thinking *и* вызов инструмента в одном ответе, и чатовые 8192 выбирались
  (8012 токенов) без единой записи в файл;
- **ни один процесс не переживает своё задание**: по таймауту умирает всё
  дерево (группа + обход по родителям, потому что инструментальные шеллы `pi`
  детачатся), а после каждого прогона свип убивает всё, у чего cwd — рабочая
  копия задания: собственный `python -m http.server 8770 &` модели переживает
  и *чистый* выход агента, держит жёстко прошитый порт, и следующий такой же
  self-check виснет на занятом порту весь wall clock. Тот же свип висит на
  `atexit`: выход в обход `finally` (отладчик, `Py_Exit`) не разворачивает стек,
  и без хука сирота переживает уже весь прогон.

Отсутствие `pi` — ошибка конфигурации, а не «не проверено»: прогон ставит его
сам при первом обращении, `make agent` делает это заранее, `dailybench doctor`
сообщает, где он (или какой командой ставится). `DAILYBENCH_AGENT_BIN`
указывает на конкретный бинарник.

## Визуальные блоки (измеряются, но вне общего счёта)

| Ключ | Блок | Заданий | Что именно проверяется |
|---|---|---:|---|
| K | Визуальные симуляции (Three.js r186) | 20 | Страницу пишет агент в `index.html`; запускается в headless Chromium, отдаёт сцену через `window.__probe()`, шагает ровно на `window.__step(dt)` и рисует воспроизводимый кадр 800×600 |
| L | Свободная арт-работа | 1 | Файл `index.html` пишет агент; способ рисования модель выбирает сама (HTML/CSS, SVG, Canvas, WebGL; локальный Three.js доступен, но не обязателен). Автоматика проверяет только техническую доставку: страница загрузилась без внешних ресурсов и ошибок, кадр 1920×1080 снят. Художественное качество оценивает человек по кадрам витрины |

Каждое задание спрашивает одно: умеет ли модель собрать *работающую* страницу —
баллистика, маятники, коробка соударений, фонтан частиц, стая, диффузия тепла,
клеточные автоматы, терраин, 3D-гистограмма, оррерия, двухзвенный манипулятор?
Четыре проверки по баллу (html, scene, simulation, image) снимаются прямо из
браузера: состояние сцены, состояние после заданного числа шагов (независимо
пересчитанное на Python по той же схеме) и сам кадр.

Оба блока намеренно не входят в вердикт: сборка браузера на машине измерения не
должна двигать балл качества. Кадры копируются в каталог прогона и собираются в
галерею `visual.html` — так у лидерборда появляется экран, который показывает,
что модель действительно нарисовала.

Библиотека зафиксирована и лежит в репозитории (`vendor/three/`, r186,
контрольные суммы в `vendor/three/PROVENANCE.md`); страница может импортировать
только `./vendor/three.module.js`, а любой запрос за пределы loopback
отклоняется и попадает в отчёт. Для блока нужны `playwright` и Chromium
(`make browser`); без них блок помечается как непроверенный, а не падает.
Правила написания новых сценариев — `docs/visual-contract.md`, арт-сцен —
`docs/art-contract.md`.

Арт-блок спрашивает не то, что блок симуляций: модель получает свободный бриф
и сама выбирает идею, стиль и средства. Промпт не предписывает палитру,
композицию, воспроизводимость кадров или обязательные хуки (`__probe`,
`__step`, `__ready`); статичная страница допустима, анимация — по желанию
автора. Единственная автоматическая проверка — техническая доставка
(страница загрузилась, кадр снят); вкус человека автоматическими баллами не
измеряется.

## Правила честности (одинаковые для всех моделей)

- **Декодирование**: `temperature=0`, `top_p=1`, seed задания выводится из
  мастер-seed'а, одинаковые бюджеты ответа (`4096` токенов, `8192` для
  категории, которая пишет целый артефакт), одинаковые потолки суммарной
  генерации и числа вызовов инструментов.
- **Fixture'ы**: порождаются из пары `(мастер-seed, id задания)`, никогда не
  переиспользуются между заданиями; `suite.json` публикует SHA-256 каждого
  промпта, так что опубликованный прогон привязан к конкретному сьюту.
- **Длинный контекст измеряется, а не оценивается**: документы подгоняются под
  реальный токенизатор на старте прогона (`calibrate_chars_per_token`), и
  документ, не добравший объём, или запрос, не влезший в окно, помечается как
  *недопуск* — это не результат качества.
- **Непроверенное — не ноль**: категория, которую конфигурация не умеет или сценарий, который нельзя проверить на этой машине, вычитается и из числителя, и из
  знаменателя.
- **Доверие к probe (K)**: чеки сцены читают значения `window.__probe()`,
  которые сама страница и отчитывает. Страница может захардкодить их вместо
  чтения собственной сцены — в аудите это фиксируется как ошибка модели
  (контракт требует фактические значения), но возможное ужесточение —
  читать `camera.position` напрямую из JS-контекста.
- **Происхождение**: путь и SHA-256 весов, сборка рантайма, квант, тип KV-кэша,
  окно контекста, режим offload и точная командная строка запуска сервера
  записываются в каталог прогона.

## Отчёт

`report` собирает две разновидности одной страницы из одного рендера:

* **`<прогон>/report.html`** — полный отчёт по одной модели, рядом с её
  `report.md` (прогон пишет его сам, `--no-html` отключает). Свои `_vendor` и
  `_showcase` лежат рядом, поэтому каталог прогона самодостаточен: его можно
  отдать сервером, заархивировать или опубликовать как есть. Дополнительная
  вкладка — **Провенанс**: хеш весов, окно, бюджеты, каркас агента, хеш сьюта.
* **`comparison.html`** — поле моделей, а `--compare метка,метка` явно выбирает,
  кого сравнивать (метка, id модели или имя каталога; порядок сохраняется).

Обе страницы офлайн (plotly и three.js лежат рядом в `_vendor` и `_showcase`,
сеть не нужна). Вкладки страницы сравнения:

* **Решения моделей** — баллы, карточки моделей с потерями по категориям,
  документированный расход (токены ответа, токены размышлений, секунды);
* **Решения моделей по сьюту** — матрица «задание × модель»: одна строка — одно
  задание, столбец — модель, цвет ячейки — полнота решения, подсказка — какая
  проверка провалена. Фильтры: только балльные, только витрина, только с потерями;
* **Графики** — plotly: качество по категориям, K и L рядом, расход токенов
  отдельно на ответ и на размышления, цена результата (балл за минуту),
  размышления против качества;
* **Витрина** — все кадры K/L; клик открывает **живую страницу, которую написал
  модель**, рядом с кадром. «Режим съёмки» разворачивает сцену на весь экран,
  ←/→ листают задачи, пробел двигает симуляцию, Esc закрывает; «сравнить
  выбранные» ставит страницы нескольких моделей рядом и шагает их синхронно.

ES-модули не грузятся с `file://`, поэтому для живых сцен поднимите сервер:

```bash
make serve DIR=runs        # http://127.0.0.1:8765/comparison.html
```

## От прогона к лидерборду

1. `scripts/sweep.py` проходит по `configs/reference.json`, поднимает каждую
   конфигурацию через собственный API рантайма, прогоняет `preflight --full`,
   затем сьют, и ведёт `runs/sweep-summary.json`.
2. `dailybench report runs/*` рисует по одному `report.md` на прогон и общий
   `comparison.md`, где рядом стоят вердикт качества, проценты по категориям,
   TTFT на длинном промпте, скорость генерации и пиковая VRAM.
3. Ранжирование идёт по вердикту (`заработано/возможно`) — он уже исключает
   пропущенное и недопущенное, колонки по категориям показывают, *где* именно
   конфигурация выигрывает, а колонка витрины и галерея `visual/` — что она
   нарисовала.

Каталог прогона самодостаточен: `config.json`, `suite.json`, `provider.json`,
`hardware.json`, `scores.json`, `tasks.json` и `transcripts/<task>.json` — поэтому
опубликованное число можно воспроизвести или пересчитать без GPU.

## Опубликованные артефакты и фреймворк записи

`docs/ARTIFACTS.md` перечисляет, что сознательно лежит в git (один
опубликованный прогон и его сравнение), а что остаётся локальным, включая
записи и видео-архив, — с командами проверки восстановленного архива.
`docs/recording/` — самостоятельный набор для записи живых веб-сцен:
покадровый рекордер, пакетный драйвер, драйвер страницы, практики и грабли,
которые здесь стоили реального времени.

## Как добавить категорию

Категория — это один модуль в `dailybench/tasks/`, который регистрирует себя:

```python
IDS = ("K-1", "K-2")

def generate(rng, cfg):        # детерминирован по rng: ни часов, ни сети
    ...

def evaluate(task, tr):        # оценивает наблюдаемый результат, а не форму транскрипта
    ...

core.register(key="K", title="…", points=…, generate=generate, evaluate=evaluate, expected_ids=IDS)
```

Правила, которые сьют проверяет сам (полный контракт — в `dailybench/core.py`):

- `generate` детерминирован по `rng` и обязан подтверждать все утверждения своих
  fixture'ов (задуманный дистрактор действительно отличается от ответа, ответ
  единственен, в документе действительно есть нужные факты).
- Сумма проверок задания равна его `max_points`.
- Эталонный ответ набирает полный балл, мусорный — ноль; иначе
  `dailybench selfcheck` валит сборку.
- Новый модуль добавляется в `dailybench/tasks/__init__.py`, а балл категории —
  в `CATEGORY_POINTS` (реестр не примет расхождение).

## Разработка

```
make test     # pytest
make cov      # pytest --cov=dailybench
make selfcheck
```

Нужен Python ≥ 3.10 и никаких сторонних зависимостей в рантайме; для тестов —
только `pytest` (`make setup`). Категориям C, K и L нужен `pi` (`make agent`),
визуальным — ещё `playwright` с Chromium (`make browser`); чат-прогон работает
без обоих (`--no-agent`). `nvidia-smi`, `go` и Docker необязательны: harness
определяет, что есть на машине, и сообщает, что проверить не может, вместо того
чтобы угадывать, — а найденный toolchain добавляется в `PATH` агента, чтобы тот
не был измерен на худшей информации, чем evaluator.

## Что остаётся локальным (endpoint'ы, ключи, пути машины)

Репозиторий публичный, машина измерения — нет. В git не обязано ехать ничего
машинно-специфичного, и перед пушем не нужно вычищать приватное:

| Что | Где живёт | Как переопределить |
|---|---|---|
| API-ключ | только окружение, в трекаемых файлах значения нет | `export DAILYBENCH_API_KEY=sk-…` (по умолчанию `not-needed`) |
| Endpoint и модель | трекаемый дефолт `127.0.0.1:1234/v1` + `local-model` | `export DAILYBENCH_BASE_URL=…`, `export DAILYBENCH_MODEL=…` |
| Эталонные конфигурации (абсолютные пути к весам, порты, теги) | `configs/reference.json` (в git, 13 записей) | `export DAILYBENCH_REFERENCE=configs/reference.local.json` — этот файл в `.gitignore` |
| Прогоны, серверные логи, sweep-summary | `runs/` | в `.gitignore` |
| Кэш отрисованных кадров (ключ с версией) | `~/.cache/dailybench/visual` | `DAILYBENCH_VISUAL_CACHE` |
| Бинарник агента | ищется в `PATH` и типовых префиксах | `export DAILYBENCH_AGENT_BIN=/path/to/pi` |

`configs/reference.json` едет и как рабочий пример, и как таблица-фолбэк внутри
`dailybench/reference.py`; тест падает, если они разойдутся. Абсолютные пути
(`C:\\Users\\…`, `/Users/…`) разрешены ровно в этих двух местах — тест обходит
остальные файлы и падает на третьей копии.

Свежий клон запускается после двух export'ов:

```bash
export DAILYBENCH_BASE_URL=http://127.0.0.1:8888/v1
export DAILYBENCH_API_KEY=sk-local
python -m dailybench bench --config qwen3.8-27b-ud-q3-k-xl
```

`dailybench doctor` печатает итоговый endpoint — видно, с кем будет говорить
прогон; сам ключ не печатается (важно лишь его наличие), но попадает в
`runs/<name>/config.json`, потому что прогон обязан воспроизводиться.

## Откуда берутся числа

- `configs/reference.json` хранит политику (декодирование, бюджеты, окно, тип
  KV-кэша, правила prompt cache и RoPE) и по записи на каждую измеряемую
  конфигурацию; точная командная строка запуска входит в отчёт.
- `suite/<seed>/` хранит порождённый сьют и его дайджест; `oracles.json`
  содержит ответы и намеренно не попадает в публикуемый `prompts.json`.
