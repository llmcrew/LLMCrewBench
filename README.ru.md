# LLMCrew DailyBench

Детерминированный бенчмарк для **локальных** языковых моделей с оценкой по
наблюдаемым результатам. Бюджет — 16 ГиБ VRAM, поэтому внутри репозитория сьют
называется *DailyBench-16*.

Десять балльных категорий: в замороженном baseline 47 заданий A–J и 100
баллов, плюс два **визуальных блока** (20 сценариев симуляций и 29 арт-работ;
в `stretch-v1` — 36 и 39), которые измеряются в headless-браузере и
показываются вне общего счёта. Каждый балл берётся из проверяемого результата — разобранного
ответа, файла на диске, прогона скрытых тестов, журнала вызовов инструментов,
отрисованного кадра — и никогда из вердикта модели-судьи. Сьют целиком
порождается из одного seed'а: два прогона двух квантизаций получают
побайтово одинаковые задания.

```
make setup                       # .venv + pytest (uv)
make agent                       # pi — агентный рантайм категорий C/K/L
make selfcheck                   # без GPU: генераторы и evaluator'ы должны сойтись
python -m dailybench bench --config qwen3.8-27b-ud-q3-k-xl --speed
python -m dailybench report runs/qwen3.8-27b-ud-q3-k-xl runs/qwen3.8-27b-ud-iq3-s
```

## Что сравнивает лидерборд

Одна строка — одна *конфигурация* (модель + квант + рантайм + тип KV-кэша +
окно контекста), а не имя модели: одни и те же веса в `Q3_K_XL` и `IQ2_S` — это
разные результаты. В отчёте видно, что именно измерено, на какой GPU, какой
командой запуска и с какой SHA-256 файла весов.

Качество и скорость не смешиваются: качество — сумма баллов, скорость —
отдельный профиль (TTFT, скорость префилла и генерации, пиковая VRAM на
заполненном контексте). Конфигурация, которая не помещается в бюджет или не
прошла допуск по длинному контексту, так и помечается: непроверенное никогда не
превращается в ноль баллов.

| F | Устойчивость к галлюцинациям | 8 | 1 | 10 вопросов: 5 с ответом, 5 без — каждая выдумка снимает баллы своего вопроса |

Внутри отчёта каждая категория нормируется в 0–100 %, итог — сумма заработанных

Числа таблицы — baseline. `stretch-v1` добавляет id из таблицы «Профили»,
в порядке `build_suite`, не меняя 100 баллов A–J: итог категории
делится между её задачами поровну (`suite.apply_profile_weights`, см.
«Профили»).

## Профили

`core.PROFILES` принимает четыре профиля. Профиль пишется в `config.json` и
`suite.json`; `resume` и `rescore` отказываются смешивать разные профили.

| Профиль | Что в нём |
|---|---|
| `baseline-20261020` (по умолчанию) | Замороженный рейтинговый сьют: 47 заданий A–J, 100 баллов, K-1…K-20, L-1…L-29 |
| `pilot` | Только сценарии, не допущенные к рейтингу: IF-6, R-16, C-4, T-8, LC-6, F-2, G-5, H-4, I-3, J-3, визуальные хосты K-21, K-23, K-25 и L-1…L-29 — 42 задания |
| `stretch-v1` | Baseline плюс каждый id, который добавляет `build_suite`, в порядке сьюта: IF-6, IF-7, IF-7-KK, IF-7-EN, IF-8, IF-9, IF-10, R-16, R-17, R-17-KK, R-18, C-4, C-5, C-6, N-2, C-7, N-9, T-8, T-9, T-10, T-11, LC-6, LC-7, LC-8, F-2, F-3, G-5, H-4, H-5, I-3, I-4, I-5, J-3, J-4, J-5, K-21…K-36, L-30…L-39 — 82 задания A–J, 36 K, 39 L; не менее пятой части каждой категории A–J приватны |
| `research-v1` | Десять текстовых исследовательских сценариев (IF-9, IF-10, N-2, T-10, T-11, T-12, LC-8, F-3, I-5, J-5) плюс VQA-трек V-1…V-6 (6 справочных баллов, подпись отдельно от K, вне 71). Семь балльных категорий (A, C, D, E, F, I, J), 71 балл; B, G, H, K и L отсутствуют, поэтому профиль не ранжируется с baseline |

`pilot` не сводится к новому итогу `/100`: задачи A–J сохраняют веса, объявленные
модулями, и читаются по отдельности. Профиль не ранжируется с baseline.
`stretch-v1` держит итог A–J на 100 и растит
только витрину (K 144 балла, L 39 справочно). `research-v1` объявляет только
те категории, которые несёт, поэтому его знаменатель 71, а 6 справочных баллов V
лежат вне него и подписываются отдельно от K. Отчёт помечает `pilot` и
`research-v1` как неранжируемые с baseline. `apply_profile_weights` раскладывает
объявленный итог категории по её задачам, округлительный хвост достаётся
последней, поэтому сумма ровно объявленная. Веса ставятся до фильтра `--only`,
так что срез сохраняет вес задачи в полном профиле.

Каждый профиль сверяется с точным списком id
(`CategoryModule.expected_ids_by_profile`, `tasks/visual.PILOT_IDS`): модуль,
собравший другой список, валит прогон, а не молча ужимает категорию.

## Статусы результата

У каждой строки баллов есть `status` = `ok`, `skipped` или `error`. Причины
пропуска не смешиваются: `not_run` (задачи нет в прогоне), `model_failed`
(задача была, страница не доставлена или страница падает до кадра),
`evaluator_unavailable` (на машине нет браузера, Go или подобного),
`capture_failed` (страница жива, запись сорвалась), `media_missing` (клипа нет
на диске). Строка `ok` при этом может быть частичной.

Допуск — отдельная ось: `unverified` значит, что runtime не сообщил размер
входа, — числитель и знаменатель остаются полными, и вердикт так и говорит,
вместо угаданного нуля. Обе части из числителя и знаменателя выводит только
`skipped`; недопуск (`failed`) показывается вердиктом по доступным баллам.

Исчерпание объявленного предела — `--request-wall-clock` (по умолчанию 1800 с)
или предел задачи, включая сокет, дошедший до этого потолка, — это
`resource_exhausted`: 0 баллов, задача остаётся в знаменателе, прогон ранжируем.
`resume` наследует сохранённый `request_wall_clock`, если флаг не передан снова.
Обрыв, не достигший предела (connection refused, reset), остаётся `infra_failure`
и не ранжируется. `--retry-errors` перезапускает только `infra_failure` и
`evaluator_failure`. `--allow-suite-drift` сохраняет строки, чьи байты задачи не
изменились, и дописывает решение в `resume_log.jsonl`.

Windows, Linux и macOS поддерживаются (CI включает `windows-latest`; Makefile
на Windows берёт `.venv/Scripts/python.exe`). Агентные категории при доступном
Docker идут в песочнице: per-run internal-сеть, egress только через forwarder
к endpoint, образы закреплены по id. Host gateway агенту не выдаётся. Сравнение
ранжирует прогон только при совпадении ключа контракта
(`suite_sha256:generation_mode`); прогон без записанного режима не ранжируется
(«режим генерации не записан»).

## Слои доказательств

Три артефакта не смешиваются:

* **original** — ответ ровно в том виде, в каком его оценивали (агентский
  `index.html` или fenced-блок чата), и кадр, который оценивали проверки. Хеш
  кадра — SHA-256 от байт на диске, пересчитывается при каждом чтении кэша;
* **display** — `pages/<id>.html` отчёта: original плюс хук `__dbscene`,
  переписанные импорты `./vendor/three.module.js` на автономный бандл
  `three.global.js`, подпись и (для K) масштабирование под окно. Для L свежий
  захват — это *некоторый* кадр той же работы, не обязательно побайтово тот,
  что оценивали;
* **capture** — видео: кадры JPEG q90, кодирование H.264 CRF 21 / yuv420p.
  Слой lossy по построению, поэтому клип никогда не выдаётся за оценённый кадр;
  рядом лежит маркер статуса с причиной. Клипы производит и хранит отдельный
  репозиторий `llmcrew/LLMCrewBenchRecoder`.

Содержательный хеш (`shot_sha`, SHA-256 от байт файла) есть только у оценённого
кадра; display-страницы и клипы — производные, их идентифицирует путь.
Display-страница и preview никогда не подменяют original-доказательство.

## Лимит ответа: окно, а не лабораторный потолок

Новые прогоны против endpoint по умолчанию используют **262 144 токена (256К)**,
включая контекст Pi для C/K/L. Другой размер задаётся через `--context-window`.
Сам endpoint должен поддерживать это окно и быть настроен на него: флаг
не перенастраивает внешний сервер.

Явный `--config` сохраняет окно своей эталонной записи; существующие аппаратные
профили на 32К/128К автоматически не увеличиваются. Шаблон `generic-gguf` теперь
использует 256К. Для нового сравнения через reference нужно указать новое окно
в записи и проверить загруженный сервер командой `preflight --full`.
Сохранённые результаты не меняются; при `--resume` старого endpoint-прогона
нужно указать его исходный `--context-window`, не смешивая измерения 32К и 256К.

Лимит ответа — окно модели минус промпт (`unbounded_budget`), а
`--max-new-tokens` задаёт верхнюю границу поверх него: меньшее из двух уходит в
запрос, реально отправленный бюджет и причина пишутся в транскрипт, а floor 256
не выдаётся за измеренное место. Если модель потратила 100 КБ на размышления и
не дошла до текста — это её результат, а не наш потолок, и расход документируется
обязательными полями (`spend` в каждом транскрипте: токены ответа, токены
размышлений, секунды, TTFT, скорость). `reasoning_effort` не форсируется — стенд
отдаёт свой дефолт, и это часть провенанса; потолок thinking задаётся
`--reasoning-budget` (2048), режим `--generation-mode native` отдаёт sampling и
thinking серверу. Оба режима и весь ушедший контракт записываются в транскрипт.
Старый режим с таблицей бюджетов остаётся: `unbounded_budget = False`.

## Артефакты собирает агент, а не диктовка в чат

Три категории, которые производят *файл* (C — код, K/L — визуальные страницы),
решает не один промпт с разбором ответа, а кодинг-агент
[`pi`](https://pi.dev) в копии репозитория задачи: он читает файлы, правит их,
запускает собственные тесты проекта, и **оценка идёт по тому, что осталось на
диске** — модель, которая «ответила верно», но файл не записала, работу не
закончила.

Чат-путь остаётся для нарративных категорий (A, B, D, E, F, G, H, I, J) — там
честная форма задачи именно такая, — и доступен для C/K/L флагом `--no-agent`,
так что два каркаса можно сравнить на одном сьюте.

Инварианты каркаса (одинаковые для всех моделей, проверяются тестами):

- **пришпиленный агент**: ровно `pi 1.0.0`
  (`npm install -g @earendil-works/pi-coding-agent@1.0.0`), инструменты
  `read,bash,edit,write`; каждый старт выполняет `pi --version`, другая версия
  отвергается с этой install-командой, а не ведётся непонятным ей argv (0.80.10 не
  знает разделителя `--` и умирала до первого запроса); пришедшая версия и sha256
  бинарника пишутся в транскрипт и в identity прогона;
- **изоляция от машины**: `--no-session` (никакого состояния между заданиями),
  `--no-context-files` (свой `AGENTS.md` репозитория не должен вписываться в
  промпт), `--no-extensions --no-skills --no-prompt-templates` (`.pi/`, который
  создаст модель, не меняет каркас), `--offline` (без обновления каталога и
  телеметрии), `--no-approve`;
- **один endpoint, один ключ**: одноразовый `PI_CODING_AGENT_DIR` со
  сгенерированным `models.json` — только endpoint прогона, политика
  `temperature=0`/`top_p=1` и потолок ответа категории;
- **никаких подсказок**: рабочая копия содержит ровно фикстуру (плюс
  пришпиленный `vendor/three.js` для K/L); `AGENTS.md` агента сообщает только,
  где библиотека и какой файл оценивается;
- **toolchain доступен агенту**: `PATH` дополняется Go SDK, который бенчмарк
  находит сам, — агент не может быть измерен на худшей информации, чем
  evaluator;
- **отчёт агента — это провенанс**: поток JSON-событий → вызовы инструментов,
  ходы, расход токенов; упавший агент сохраняет события и хвост stderr вместо
  того, чтобы быть оценённым как пустой каталог.
- **пустой stdin**: `pi` читает stdin, если это пайп, и ждёт EOF, поэтому запуск
  идёт с `DEVNULL` — иначе прогон из шелл-пайпа висит весь wall clock без единого
  события;
- **потолок ответа — оконный бюджет**, а не чат-таблица: агент тратит его на
  thinking *и* вызов инструмента в одном ответе, и чатовые 8192 выбирались
  (8012 токенов) без единой записи в файл;
- **ни один процесс не переживает своё задание**: по таймауту умирает всё
  дерево (группа + обход по родителям, потому что инструментальные шеллы `pi`
  детачатся), а после каждого прогона свип убивает всё, у чего cwd — рабочая
  копия задания: собственный `python -m http.server 8770 &` модели переживает
  и *чистый* выход агента, держит жёстко прошитый порт, и следующий такой же
  self-check виснет на занятом порту весь wall clock. Тот же свип висит на
  `atexit`: выход в обход `finally` (отладчик, `Py_Exit`) не разворачивает стек,
  и без хука сирота переживает уже весь прогон.

Отсутствие `pi` — ошибка конфигурации, а не «не проверено»: прогон ставит
пришпиленную версию сам при первом обращении, `make agent` делает это заранее,
`dailybench doctor` сообщает, где он (или какой командой ставится). Чужая версия —
такая же ошибка: она называет ожидаемый релиз и install-команду, вместо того чтобы
оценить пустую рабочую копию. `DAILYBENCH_AGENT_BIN` указывает на конкретный
бинарник; он проверяется так же.

## Визуальные блоки (измеряются, но вне общего счёта)

| Ключ | Блок | Баллы (baseline / stretch) | Заданий (baseline / stretch) | Что именно проверяется |
|---|---|---:|---:|---|
| K | Визуальные симуляции (Three.js r186) | 80 / 144 | 20 / 36 | Страницу пишет агент в `index.html`; запускается в headless Chromium, отдаёт сцену через `window.__probe()`, шагает ровно на `window.__step(dt)` и рисует воспроизводимый кадр 800×600 |
| L | Свободная арт-работа | 29 / 39 (справочно) | 29 / 39 | Файл `index.html` пишет агент; `L-1` — совсем свободная работа, у остальных 28 (38 в stretch, вплоть до `L-39`) назван только сюжет; способ рисования модель выбирает сама (HTML/CSS, SVG, Canvas, WebGL; локальный Three.js доступен, но не обязателен). Единственная проверка в 1 балл — техническая доставка: страница загрузилась без внешних ресурсов и ошибок, кадр 1920×1080 снят |

Каждое задание спрашивает одно: умеет ли модель собрать *работающую* страницу —
баллистика, маятники, коробка соударений, фонтан частиц, стая, диффузия тепла,
клеточные автоматы, терраин, 3D-гистограмма, оррерия, двухзвенный манипулятор?
Четыре проверки по баллу (html, scene, simulation, image) снимаются прямо из
браузера: состояние сцены, состояние после заданного числа шагов (независимо
пересчитанное на Python по той же схеме) и сам кадр.

K — 80 баллов на K-1…K-20 в baseline, 12 баллов на трёх хостах K-21/K-23/K-25
в `pilot` и 144 балла на K-1…K-36 в `stretch-v1`. L даёт 1 балл за работу и
только за доставку, поэтому его итог — 29 или 39 и остаётся справочным:
художественное качество оценивает человек по кадрам витрины.

Оба блока намеренно не входят в вердикт: сборка браузера на машине измерения не
должна двигать балл качества. Кадры копируются в каталог прогона и собираются в
галерею `visual.html` — так у лидерборда появляется экран, который показывает,
что модель действительно нарисовала.

Библиотека зафиксирована и лежит в репозитории (`vendor/three/`, r186,
контрольные суммы в `vendor/three/PROVENANCE.md`); страница может импортировать
только `./vendor/three.module.js`, а любой запрос за пределы loopback
отклоняется и попадает в отчёт. Для блока нужны `playwright` и Chromium
(`make browser`); без них блок помечается как непроверенный, а не падает.
Правила написания новых сценариев — `docs/visual-contract.md`, арт-сцен —
`docs/art-contract.md`.

Арт-блок спрашивает не то, что блок симуляций: `L-1` — свободный бриф без
темы, у остальных назван только сюжет; композицию, стиль и средства модель
выбирает сама. Промпт не предписывает ни палитру, ни формулы,
ни воспроизводимость кадров, ни обязательные хуки (`__probe`, `__step`,
`__ready`); статичная страница допустима, анимация — по желанию автора.
Единственная автоматическая проверка — техническая доставка (страница
загрузилась, кадр снят); вкус человека автоматическими баллами не измеряется.

## Правила честности (одинаковые для всех моделей)

- **Декодирование**: `temperature=0`, `top_p=1`, seed задания выводится из
  мастер-seed'а, одинаковые бюджеты ответа (`4096` токенов, `8192` для
  категории, которая пишет целый артефакт), одинаковые потолки суммарной
  генерации и числа вызовов инструментов.
- **Fixture'ы**: порождаются из пары `(мастер-seed, id задания)`, никогда не
  переиспользуются между заданиями; `suite.json` публикует SHA-256 каждого
  промпта, так что опубликованный прогон привязан к конкретному сьюту, а также
  веса задач и контракт evaluator'а (поднятый `core.EVALUATOR_CONTRACT` или
  изменённый модуль проверки — другое измерение).
- **Длинный контекст измеряется, а не оценивается**: документы подгоняются под
  реальный токенизатор на старте прогона (`calibrate_chars_per_token`), и
  документ, не добравший объём, или запрос, не влезший в окно, помечается как
  *недопуск* — это не результат качества.
- **Непроверенное — не ноль**: категория, которую конфигурация не умеет или сценарий, который нельзя проверить на этой машине, вычитается и из числителя, и из
  знаменателя.
- **Probe — не oracle**: проверки `scene` и `simulation` сверяют
  `window.__probe()` — числа, которые отчитывает сама страница, — с независимым
  пересчётом той же схемы на Python. Значения округлены до 4 знаков;
  `visual.near` по умолчанию `1e-3`, целые счётчики и шаги — `0`, отдельные
  величины строже (`1e-4`/`1e-6`), поэтому допуск выводится из округления и
  межъязыкового накопления, а не копируется. Пиксельные проверки разреженно
  читают крупнейший видимый canvas (`PIXEL_PROBE`), что не доказывает, что
  именно он доминирует в скриншоте. Страница, вернувшая ожидаемые числа без
  симуляции, проходит; в аудите это фиксируется как ошибка модели — контракт
  требует фактические значения.
- **Происхождение**: путь и SHA-256 весов, сборка рантайма, квант, тип KV-кэша,
  окно контекста, режим offload и точная командная строка запуска сервера
  записываются в каталог прогона.

## Команды

| Команда | Назначение |
|---|---|
| `make setup` | создать `.venv` и поставить pytest |
| `dailybench selfcheck` | проиграть все задания эталонным и мусорным ответом: и то и другое должно попасть туда, куда задумано. GPU не нужен |
| `dailybench list` | показать порождённый сьют (id, баллы, размеры) |
| `dailybench generate --out suite/<seed>` | записать `prompts.json` (можно публиковать) и `oracles.json` (ответы); `--profile` выбирает версию сьюта |
| `dailybench doctor` | GPU, toolchain, агентский рантайм, доступность endpoint'а и токенизатора |
| `dailybench preflight --config <id> --full` | сверить запущенный рантайм с эталонной конфигурацией |
| `dailybench visual <page.html> --steps N` | отрисовать одну страницу ровно так, как это делает проверка (probe, кадр, метрики кадра) |
| `dailybench bench --config <id> --speed` | поднять рантайм, preflight, прогнать сьют и записать `report.md` + `report.html` (`--no-html` — без страницы) |
| `dailybench run --base-url … --model …` | тот же сьют против уже запущенного endpoint'а (`--no-agent` оставляет C/K/L на чат-пути); результат пишется на диск после каждого задания, поэтому падение процесса на 90-м не теряет первые 89. `--resume` догружает прерванный прогон в тот же каталог: сохранённые задачи не пересъёмлются, оборванные (таймаут, reboot) пере-прогоняются, калибровка берётся из сохранённого `config.json`, веса задач, общий знаменатель и полная identity прогона (конфигурация, бюджеты, режим агента, версия harness) сверяются, а читается только та generation, у которой каждый файл сходится с хешем в манифесте |
| `dailybench report <каталоги…>` | пересобрать `report.md`, по одному `<прогон>/report.html`, `comparison.md` и `comparison.html` (`--no-html` — без страниц, `--compare` — кого сравнивать) |
| `dailybench rescore <каталог>` | пересчитать баллы сохранённых транскриптов текущими evaluator'ами — без вызова модели; разошедшаяся фикстура сохраняет старый балл и помечается (legacy `suite.json` без per-task строк сверяется по хешу всего сьюта) |
| `scripts/sweep.py` | по очереди поднять все эталонные конфигурации и прогнать весь сьют |

`--profile baseline-20261020` — замороженный рейтинговый сьют (47 A–J, 100 баллов).
`pilot` показывает только ещё не допущенные сценарии (см. «Профили») и не
сводится к новому итогу `/100`; веса его задач A–J остаются модульными.
`stretch-v1` добавляет сценарии сверх baseline, сохраняя те же 100 баллов A–J:
вес категории делится между её задачами поровну, витрина растёт до K 144 / L 39.
Runtime, не сообщивший размер входа, оставляет допуск `unverified`, а не валит
его. Профиль пишется в `config.json` и `suite.json`; `resume` и `rescore`
отказываются смешивать разные профили. Каждый
checkpoint несёт полную identity прогона (конфигурация, бюджеты, режим агента,
дайджест сьюта, версия harness), и `resume` отклоняет каталог чужого прогона;
веса задач и общий знаменатель сверяются отдельно, а generation читается только
та, у которой каждый файл сходится с хешем в манифесте; зеркала принимаются
только при той же identity и наличии master.

## Отчёт

`report` собирает две разновидности одной страницы из одного рендера:

* **`<прогон>/report.html`** — полный отчёт по одной модели, рядом с её
  `report.md` (прогон пишет его сам, `--no-html` отключает). Свои `_vendor` и
  `_showcase` лежат рядом, поэтому каталог прогона самодостаточен: его можно
  отдать сервером, заархивировать или опубликовать как есть. Дополнительная
  вкладка — **Провенанс**: хеш весов, окно, бюджеты, каркас агента, хеш сьюта.
* **`comparison.html`** — поле моделей, а `--compare метка,метка` явно выбирает,
  кого сравнивать (метка, id модели или имя каталога; порядок сохраняется).

Обе страницы офлайн (plotly и three.js лежат рядом в `_vendor` и `_showcase`,
сеть не нужна). Вкладки страницы сравнения:

* **Решения моделей** — баллы, карточки моделей с потерями по категориям,
  документированный расход (токены ответа, токены размышлений, секунды);
* **Решения моделей по сьюту** — матрица «задание × модель»: одна строка — одно
  задание, столбец — модель, цвет ячейки — полнота решения, подсказка — какая
  проверка провалена. Фильтры: только балльные, только витрина, только с потерями;
* **Графики** — plotly: качество по категориям, K и L рядом, расход токенов
  отдельно на ответ и на размышления, цена результата (балл за минуту),
  размышления против качества;
* **Витрина** — все кадры K/L; клик открывает **живую страницу, которую написал
  модель**, рядом с кадром. «Режим съёмки» разворачивает сцену на весь экран,
  ←/→ листают задачи, пробел двигает симуляцию, Esc закрывает; «сравнить
  выбранные» ставит страницы нескольких моделей рядом и шагает их синхронно.

ES-модули не грузятся с `file://`, поэтому для живых сцен поднимите сервер:

```bash
make serve DIR=runs        # http://127.0.0.1:8765/comparison.html
```

## От прогона к лидерборду

1. `scripts/sweep.py` проходит по `configs/reference.json`, поднимает каждую
   конфигурацию через собственный API рантайма, прогоняет `preflight --full`,
   затем сьют, и ведёт `runs/sweep-summary.json`.
2. `dailybench report runs/*` рисует по одному `report.md` на прогон и общий
   `comparison.md`, где рядом стоят вердикт качества, проценты по категориям,
   TTFT на длинном промпте, скорость генерации и пиковая VRAM.
3. Ранжирование идёт по вердикту (`заработано/возможно`) — он уже исключает
   пропущенное и недопущенное, колонки по категориям показывают, *где* именно
   конфигурация выигрывает, а колонка витрины и галерея `visual/` — что она
   нарисовала.

Каталог прогона самодостаточен: `config.json`, `suite.json`, `provider.json`,
`hardware.json`, `scores.json`, `tasks.json` и `transcripts/<task>.json` — поэтому
опубликованное число можно воспроизвести или пересчитать без GPU.

## Опубликованные артефакты

`docs/ARTIFACTS.md` перечисляет, что сознательно лежит в git (один
опубликованный прогон и его сравнение), а что остаётся локальным, — с командами
проверки восстановленного архива. Ролик о бенчмарке — Remotion-проект, рекордер
клипов и практики записи — живёт в отдельном приватном репозитории
`llmcrew/LLMCrewBenchRecoder`; в этом репозитории видеочасти нет.

## Как добавить категорию

Категория — это один модуль в `dailybench/tasks/`, который регистрирует себя:

```python
IDS = ("K-1", "K-2")

def generate(rng, cfg):        # детерминирован по rng: ни часов, ни сети
    ...

def evaluate(task, tr):        # оценивает наблюдаемый результат, а не форму транскрипта
    ...

core.register(key="K", title="…", points=…, generate=generate, evaluate=evaluate, expected_ids=IDS)
```

Правила, которые сьют проверяет сам (полный контракт — в `dailybench/core.py`):

- `generate` детерминирован по `rng` и обязан подтверждать все утверждения своих
  fixture'ов (задуманный дистрактор действительно отличается от ответа, ответ
  единственен, в документе действительно есть нужные факты).
- Сумма проверок задания равна его `max_points`.
- Эталонный ответ набирает полный балл, мусорный — ноль; иначе
  `dailybench selfcheck` валит сборку.
- В baseline сценарий попадает только через `expected_ids`; новые объявляются в
  `IDS_BY_PROFILE` / `expected_ids_by_profile`, и `pilot`, `stretch-v1` и
  `research-v1` сверяются с точными списками — пустой список для категории,
  которую профиль не несёт.
- Новый модуль добавляется в `dailybench/tasks/__init__.py`, а балл категории —
  в `CATEGORY_POINTS` (для витрины — в `SHOWCASE_POINTS`; реестр не примет
  расхождение).

## Разработка

```
make test     # pytest
make cov      # pytest --cov=dailybench
make selfcheck
```

Нужен Python ≥ 3.10 и никаких сторонних зависимостей в рантайме; для тестов —
только `pytest` (`make setup`). Категориям C, K и L нужен `pi` (`make agent`),
визуальным — ещё `playwright` с Chromium (`make browser`); чат-прогон работает
без обоих (`--no-agent`). `nvidia-smi`, `go` и Docker необязательны: harness
определяет, что есть на машине, и сообщает, что проверить не может, вместо того
чтобы угадывать, — а найденный toolchain добавляется в `PATH` агента, чтобы тот
не был измерен на худшей информации, чем evaluator.

## Что остаётся локальным (endpoint'ы, ключи, пути машины)

Репозиторий публичный, машина измерения — нет. В git не обязано ехать ничего
машинно-специфичного, и перед пушем не нужно вычищать приватное:

| Что | Где живёт | Как переопределить |
|---|---|---|
| API-ключ | только окружение, в трекаемых файлах значения нет | `export DAILYBENCH_API_KEY=sk-…` (по умолчанию `not-needed`) |
| Endpoint и модель | трекаемый дефолт `127.0.0.1:1234/v1` + `local-model` | `export DAILYBENCH_BASE_URL=…`, `export DAILYBENCH_MODEL=…` |
| Эталонные конфигурации (абсолютные пути к весам, порты, теги) | `configs/reference.json` (в git, 13 записей) | `export DAILYBENCH_REFERENCE=configs/reference.local.json` — этот файл в `.gitignore` |
| Прогоны, серверные логи, sweep-summary | `runs/` | в `.gitignore` |
| Кэш отрисованных кадров (ключ с версией) | `~/.cache/dailybench/visual` | `DAILYBENCH_VISUAL_CACHE` |
| Бинарник агента | ищется в `PATH` и типовых префиксах | `export DAILYBENCH_AGENT_BIN=/path/to/pi` |

`configs/reference.json` едет и как рабочий пример, и как таблица-фолбэк внутри
`dailybench/reference.py`; тест падает, если они разойдутся. Абсолютные пути
(`C:\\Users\\…`, `/Users/…`) разрешены ровно в этих двух местах — тест обходит
остальные файлы и падает на третьей копии.

Свежий клон запускается после двух export'ов:

```bash
export DAILYBENCH_BASE_URL=http://127.0.0.1:8888/v1
export DAILYBENCH_API_KEY=sk-local
python -m dailybench bench --config qwen3.8-27b-ud-q3-k-xl
```

`dailybench doctor` печатает итоговый endpoint — видно, с кем будет говорить
прогон. Сам ключ не печатается и в `runs/<name>/config.json` не попадает: там
лежит только маркер `api_key_set`, а значение при пересчёте и догрузке снова
берётся из окружения.

## Откуда берутся числа

- `configs/reference.json` хранит политику (декодирование, бюджеты, окно, тип
  KV-кэша, правила prompt cache и RoPE) и по записи на каждую измеряемую
  конфигурацию; точная командная строка запуска входит в отчёт.
- `suite/<seed>/` хранит порождённый сьют и его дайджест; `oracles.json`
  содержит ответы и намеренно не попадает в публикуемый `prompts.json`.
