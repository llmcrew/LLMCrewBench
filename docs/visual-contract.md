# Категория K: контракт визуальных сценариев

Сценариев 20 в baseline (`K-1`…`K-20`) и 36 в `stretch-v1` (`K-1`…`K-36`);
`pilot` гоняет только хосты расширенных слайсов `K-21`, `K-23`, `K-25`.
Каждый сценарий стоит 4.0 и раскладывается на пять независимых проверок по
0.8: `html`, `runtime`, `scene`, `simulation`, `image`. Проверки не сворачиваются
друг в друга: ошибка консоли стоит своего `runtime` и не обнуляет кадр,
потерянный протокол — `html`/`scene`/`simulation`, но не картинку.
Баллы блока — `core.SHOWCASE_POINTS` (80 в baseline, 12 в `pilot` на трёх
хостах, 144 в `stretch-v1`); блок вне общего счёта лидерборда, но внутри
считается и сравнивается как обычно.

## Как устроен сценарий

Каждый модуль `dailybench/tasks/visual_<слайс>.py` объявляет

```python
IDS = ("K-2", "K-3", ...)          # ровно свои id, по возрастанию

def build(rng: random.Random) -> list[core.TaskInstance]:
    ...                            # детерминирован по rng, без часов и сети
```

и собирает задания через `dailybench.visual.build_task(...)`, передавая:
промпт (без общего блока требований — его допишет `visual.build_task`),
`VisualSpec` с предикатами и `golden` — эталонную страницу.

`golden` — это **эталонный ответ**, а не иллюстрация: `selfcheck` проигрывает
его как ответ модели, рендерит в браузере и требует все проверки. Поэтому каждый
сценарий обязан иметь работающую эталонную страницу.

## Что обязана сделать модель (и что проверяется)

Промпт описывает сцену и ровно три вещи, на которых держится проверка:

* `window.__probe()` — состояние сцены (точные поля перечисляются в промпте);
* `window.__step(dt)` — один детерминированный шаг симуляции на `dt` секунд;
* `window.__ready = true` — после первой отрисовки.

Проверки:

| Проверка | Что смотрит |
|---|---|
| `html` | ответ — целый документ, без внешних ресурсов **и** страница держит протокол: `__ready`, `__probe()` отвечает объектом, `__step(dt)` шагает |
| `runtime` | страница отработала без ошибок: `console.error`/`pageerror` и ни одного отказанного запроса. HTTP-загрузка и WebSocket-рукопожатие идут одним классификатором (`http`/`websocket`) и стоят одинаково |
| `scene` | состав сцены и камера из `__probe()` сразу после загрузки |
| `simulation` | `__probe()` **после** `steps` шагов по `dt` — сверка с той же схемой, посчитанной в Python |
| `image` | кадр-PNG, измеренный вне страницы: метрики цвета/области, побитовая воспроизводимость, тот же кадр на **скрытой** второй точке (`steps + half`) и согласие картинки с движением чисел probe |

`image` больше не читает canvas из realm страницы: статистика считается по
байтам скриншота в Python, поэтому чёрный `<div>` поверх canvas проваливает
`image`, а не проходит вместе с подделанным `getContext`. Скрытая вариация
шагов ловит картинку, нарисованную один раз и не связанную с симуляцией:
`__probe()` заявляет сдвиг `x`/`y` — кадр обязан смениться, и центроид класса
цвета обязан уехать в ту же сторону (рост `x` — вправо, рост `y` — вверх).
Страница с `__probe()`-арифметикой и статичным рисунком берёт `html`/`runtime`
и `scene`, и проваливает `image`.
Проверяются две пробы — объявленная точка плюс половина шагов и ранняя точка
(`steps/8`): установившийся режим (терраин, сеть в равновесии) имеет право быть
неподвижным, тогда `image` держится на объявленных предикатах, но только если
сам probe не двигает `x`/`y`.

## Правила, которые нельзя нарушать

1. **Точная схема, а не «примерно такая»**. В промпте формулируется схема шага
   (например «полунеявный Эйлер: `v -= g*dt; p += v*dt`»), и ожидаемые числа
   считаются в Python по этой же схеме. Допуск — не меньше `1e-3`: JS и Python
   по-разному группируют операции, точное равенство float запрещено.
2. **Никаких «посчитай в уме»**. Все проверки — числовые/структурные предикаты
   (`visual.near`, `between`, `contains_all`, `size_between`, `image_color`,
   `image_centroid`, `image_region`, `image_min`). Общие для всех сценариев
   условия картинки — воспроизводимость, второй скрытый момент и согласие с
   движением probe — добавляет `visual.evaluate`; объявлять их в `spec.image`
   не нужно.
3. **Кадр должен быть наглядным и устойчивым**. Объекты — заметного размера
   (шар радиусом 0.2–0.4 при камере в 12–18 единицах даёт ~30–40 px), сцена
   освещена, фон и земля различимы. Порог в `image`-проверке ставьте с запасом
   ≥2x от измеренного на эталоне значения: `image_color("warm", 0.002)` — это
   «видно ≥ 0.2 % кадра», а не «видно ровно столько».
4. **Допуск выводится, а не копируется**. `visual.near` по умолчанию `1e-3`;
   этого хватает большинству численных состояний, потому что probe округляет до
   4 знаков, а JS и Python по-разному накапливают float. Целые счётчики и шаги
   сравниваются с допуском `0`; там, где величина задана константой сцены или
   схемы (камера, вход цепи), допуск строже — `1e-4`/`1e-6`. Не поднимайте
   допуск, чтобы «прошёл» ответ с другой физикой, и не опускайте ниже
   округления probe.
5. **Probe — не oracle**. `scene` и `simulation` сверяют то, что отчитала сама
   страница, с независимым пересчётом схемы на Python; oracle — пересчёт,
   `__probe()` — недоверенный вход. Страница может захардкодить ожидаемые числа
   и не симулировать: проверки это пропустят, аудит отметит как ошибку модели.
   Компенсация арифметического probe — в `image`: пиксели считаются по самому
   PNG-скриншоту вне страницы, а на скрытой второй точке (`steps + half`)
   требуется, чтобы кадр сменился и центроид класса цвета уехал в сторону,
   которую заявил probe. Статичный рисунок с лгущими числами получает
   `html`/`runtime`/`scene`/`simulation`, но не `image`.
   Остаток риска, который принимается: `image` доказывает **видимость**
   (цвет/область/детализация есть в кадре) и **следование за probe** в грубом
   виде — направление сдвига центроида, а не точная проекция объекта. Один
   объект класса где угодно в кадре по-прежнему проходит `image_centroid`;
   перекрытие canvas непрозрачным слоем теперь видно, потому что меряется
   скриншот, а не canvas. Скрытая вариация шагов — не seed: страница, читающая
   `steps` извне, знает только объявленное число.
6. **Фикстура доказывает сама себя**. В `build()` — утверждения, на которых
   держится задание: числа различимы, ответы единственны, эталон попадает в
   кадр, ожидаемые значения не совпадают с «наивным» ответом.
7. **Эталон детерминирован**: никакого `Math.random()` без seed, никакой
   зависимости от `performance.now()`, `requestAnimationFrame` — только для
   первой отрисовки. Два рендера обязаны дать побитово одинаковый кадр
   (`preserveDrawingBuffer: true` обязателен, иначе кадр нельзя прочитать).
8. **Модель, а не библиотека**. Страница импортирует только
   `./vendor/three.module.js` (three.js r186, лежит в `vendor/three/`); никаких
   CDN, никаких аддонов (`OrbitControls` и т.п. — сами, если нужны).
9. **Ответ должен влезать в бюджет**: эталон ≤ ~150 строк, иначе 8192 токенов
   ответа не хватит — и это уже дефект задания, а не модели.

## Отладка

```bash
# отрисовать страницу точно так же, как это делает проверка
./.venv/bin/python -m dailybench visual /tmp/app.html --steps 90 --shot /tmp/app.png

# эталон задания целиком (эталон проходит, мусор 0)
./.venv/bin/python -m dailybench selfcheck --only K-2

# все задания слайса
./.venv/bin/python -m pytest tests/test_visual_<слайс>.py -q
```

Рендеры кэшируются по содержимому страницы в `~/.cache/dailybench/visual/`.
Ключ — `sha256` от JSON: `FRAME_VERSION`, render-fingerprint (байты обоих
vendor-файлов, сборка Chromium, исходник драйвера и `PIXEL_PROBE`, launch-флаги
и полный capture profile), viewport, DPR, `steps`/`dt`, режим и HTML, поэтому
повторные прогоны мгновенные, а изменённый HTML, библиотека или браузер
считаются заново. `FRAME_VERSION` остаётся ручной версией контракта, но больше
не единственный различитель: смена `PIXEL_PROBE`, флагов или viewport меняет
fingerprint сама.
`image` меряет не `PIXEL_PROBE`, а сохранённый PNG тем же разрежением
(`browser.frame_stats`, `FRAME_STATS_VERSION`): проба из страницы остаётся
диагностикой витрины, балл держится на байтах кадра. Скрытая вариация шагов —
своя запись кэша (`steps + half`), поэтому второй кадр тоже не перерисовывается
зря.
Дополнительно запись запечатана отпечатком probe (`sha256` от `probe` и
`stepped`): он известен только после рендера, поэтому в имени файла лежат
базовый ключ (без probe) и ключ с ним. На попадании отпечаток пересчитывается
из probe, сохранённого рядом с кадром, и должен совпасть с собственной печатью
записи; иначе запись считается чужой и страница перерисовывается. Так кадр
нельзя выдать за снятый с другим probe, а прежние печати того же кадра
снимаются при записи. Хеш сохранённого кадра считается от байт на диске, а не
берётся из записи, — кадр остаётся доказательством и без возможности
перерисовать страницу. Неудачный рендер не травит запись: таймаут
скриншота под нагрузкой сохраняется как `ok=false` без кадра, и следующий вызов
перерисовывает страницу. Переиспользуется только успешная запись с кадром.
Сборка отчёта кадр самовосстанавливает: если файл кэша пропал (ротация,
`rm`), витрина перерисовывает его из сырого ответа — ровно того, что оценивали
проверки; без браузера остаётся записанный путь.
Страница, которая падает до протокола (нет `__ready`, `__probe()` кидает
исключение), кадр всё равно получает: провал протокола стоит `html`/`scene`/
`simulation`, но не `image`, а картинка снимается — иначе витрина показывала бы
«живую сцену без кадра» на каждой сломанной странице. `ok` значит «кадр
снят»: ошибки консоли и потерянный протокол живут отдельными флагами
(`ready_ok`/`probe_ok`/`step_ok`) и своими проверками. `__probe()` возвращает
живой граф three.js (`mesh.parent.children[0] is mesh`), поэтому payload перед
записью проходит `browser.plain`: цикл ронял `json.dumps` кэш-записи вместе с
кадром.

## Доказательства и статусы

Original, display и capture — разные артефакты; содержательный хеш есть только у
original-кадра:

* **original** — страница ровно в том виде, в каком её оценивали (артефакт
  агента, `extract_html` без хуков), и кадр, снятый проверкой. Хеш кадра —
  SHA-256 от байт файла, пересчитывается при чтении кэша, а не берётся из
  записи;
* **display** — `pages/<id>.html` отчёта: original + `__dbscene`, импорты
  `./vendor/three.module.js` переписаны на автономный `three.global.js`, подпись
  и масштабирование сцены. Display-страница запускается с `file://`, но не
  является байтами, которые оценивали;
* **capture** — кадры записи (JPEG q90 → H.264 CRF 21/yuv420p), lossy по
  построению: клип не заменяет оценённый кадр и лежит рядом с маркером статуса.
  Display-страница и клип идентифицируются путём, а не выдаются за хешированный
  original.

Пропуск и сбой не сливаются в «модель не справилась»: `status` строки —
`ok`/`skipped`/`error`, причина пропуска — `not_run`, `model_failed`,
`evaluator_unavailable`, `capture_failed` или `media_missing`. Нет браузера —
`skipped`/`evaluator_unavailable`, а не ноль.

## Как выглядит тест слайса

`tests/test_visual_<слайс>.py` проверяет: id и баллы; сумму проверок, равную
`max_points`; детерминированность `build()` и отличие фикстур по seed; что
**каждый** эталон набирает полный балл в реальном браузере, а мусорный ответ
(«не знаю») — 0; что фикстурные утверждения из `build()` действительно
выполняются. Браузер недоступен — `pytest.skip`, потому что «не проверено» — не
ноль. Общая рубрика и её browser-негативы (ошибка консоли, чёрный overlay,
статичная картинка, отсутствие протокола, HTTP и WS) закреплены в
`tests/test_visual.py`.

## Порядок id

`K-1` — баллистика снарядов (эталонный паттерн, `visual_projectiles.py`),
дальше слайсы: `K-2..K-6` динамика и поля, `K-7..K-11` частицы и агенты,
`K-12..K-16` сетки и среды, `K-17..K-20` визуализации данных. Расширенные
слайсы: `K-21..K-22` кинематика шестерён, `K-23`/`K-26` жидкости, `K-24`/`K-25`
цепи, `K-27` очередь, `K-28` лифт, `K-29`/`K-30` конструкции, `K-31`/`K-32` орбиты и RLC-ступенька,
`K-33`/`K-34` теплоизолированная пластина и машина Атвуда, `K-35`/`K-36`
сопротивление и цепочка Verlet; в `pilot` из них
входят только `K-21`, `K-23`, `K-25`, в `stretch-v1` — все шестнадцать. Модуль
владеет своими id, поэтому пары вроде `K-23`/`K-26` не обязаны быть смежными.
Реестр (`dailybench/tasks/visual.py`) собирает модули в порядке `MODULES`,
сортирует по `ALL_IDS` и требует ровно id профиля (`PROFILE_IDS`) — свои id не
переставляйте и не перенумеровывайте.

## Агентный режим (категории C, K, L)

Страницу для блока K пишет агент `pi` в рабочей копии: файл `index.html` плюс
возможность запускать команды. Проверки не изменились — читается тот же
документ, но из файла на диске, а не из блока в ответе. Общие инварианты каркаса
(пришпиленные инструменты, `--no-session`, изолированный `PI_CODING_AGENT_DIR`,
`--no-agent` для чат-пути) описаны в `README.ru.md`.
