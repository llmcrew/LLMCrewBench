# Запись живых веб-сцен в видео: фреймворк и практики

Набор для второго применения: снять исполняющуюся веб-страницу в клип
фиксированной длины так, чтобы клип честно показывал то, что видит зритель, и
не терял движение между кадрами. Вырос из записи витрины DailyBench
(`video/tools/`), но от бенчмарка не зависит.

## Что здесь есть

| Файл | Назначение |
|---|---|
| `record_scene.py` | Запись одной сцены: headless-Chrome, CDP, покадровый JPEG, h264. Два режима: драйвер сцены и внешняя раскадровка `__step`. |
| `record_batch.py` | Пакетная запись дерева `<model>/pages/<scene>.html`, пропуск уже записанного, плашки вместо упавших страниц. |
| `page-driver.js` | Драйвер страницы: замер окна движения, развёртка на показ, `seek(n)` для записи, клавиши/сообщения. |

Быстрый старт:

```bash
python3 record_scene.py https://host/scene.html out/scene.mp4 --secs 23
python3 record_batch.py pages/ clips/ 4 23 0.6
```

## Главная идея: не записывать реальное время

Записывать «как идёт» (по таймеру, `every N ms — screenshot`) — тупик: рендер
кадра сам занимает время, шаги сцены проскакивают, клип дёргается, а скорость
записи зависит от машины. Здесь наоборот: **кадры снимаются по одному и
сцена двигается ровно на один шаг на кадр**.

* Штатный путь — драйвер (`page-driver.js`). Он замеряет, сколько шагов
  подряд canvas реально меняется, и разворачивает это окно на клип.
* Путь без драйвера — `--mode steps`: фреймворк сам зовёт `window.__step(dt)`
  (один кадр — один шаг) и `window.__probe()`, если он есть.
* Клип всегда ровно `secs × fps` кадров; ни один шаг сцены не теряется.
  Частота — параметр: снимайте с запасом над частотой показа (в DailyBench —
  120 против 60), если монтаж будет ускорять или замедлять клип; запас стоит
  и размера, и времени записи.

## Контракт страницы

Минимум, который понимает фреймворк:

```js
window.__ready = true;          // после первого кадра
window.__step = (dt) => {...};  // один детерминированный шаг
window.__probe = () => ({...}); // состояние, по желанию — и отрисовка
```

Правила, без которых запись врёт:

1. **Детерминизм**. Никакого `Math.random()` без seed и `Date.now()` в физике.
   Один и тот же шаг — один и тот же кадр.
2. **Рендер после шага, а не по таймеру**. Если страница рисует только в
   `__probe()`, драйвер перерисует сцену сам (оборачивает `WebGLRenderer`);
   без драйвера `record_scene` зовёт `__probe()` после каждого шага.
3. **Шаг не зависит от частоты кадров**. `dt` приходит аргументом; фиксировать
   его внутри страницы нельзя — клип и живой показ пойдут разным темпом.
4. **Один canvas — одна сцена** (или наоборот: если canvas несколько, сценой
   считается последний, а остальные скрываются; см. `apply_styles` в
   `video/tools/record_clip.py`).
5. **`preserveDrawingBuffer: true`** у WebGL-рендерера — иначе CDP-скриншот
   может снять пустой буфер.
6. **Без внешних запросов**: шрифты, картинки и three.js — локально; прокси и
   VPN в момент записи не должны влиять на кадр.

## Как устроен драйвер

```
__ready → замер (beat, подпись 64×48, QUIET=90 тихих шагов, потолок 1200)
        → кэш {freeze} в sessionStorage/window.name → reload
        → показ: seek(round(frame × freeze / span)), span = 4…10 с
        → пауза 0.9 с → reload (сцена начинается заново)
```

Запись вмешивается сообщением `pause` (автоплей стоит), забирает `freeze` и
вызывает `seek(round(k × freeze / (N−1)))`: первый кадр — начало окна, последний
— конец. `seek` назад не ходит, поэтому первый кадр гарантирует `seek(0)`.

Почему подпись 64×48 и сумма по всем canvas: дешёво (несколько миллисекунд),
устойчиво к сглаживанию и не ломается на страницах с двумя canvas, где первый —
WebGL без `preserveDrawingBuffer`.

## Темп: замедление — это нормально

Клип растягивает окно движения на всю длину. Множитель — `N / freeze`; для
окна 190 шагов это 7×, для 24 шагов — 57×, для одного шага — почти стоп-кадр.
Живой показ сжимает то же окно в 4–10 с, так что клип всегда медленнее.

Что с этим делать:

* не «ускорять» клип постфактум — режьте лишнее на монтаже;
* если сцена честно статична (терраин по условию, солвер сходится за шаг) —
  оставьте стоп-кадр, это правда о сцене, а не дефект записи;
* если стоп-кадр выглядит мёртвым — добавьте в сцену медленное движение
  (камера, пульсация света), не меняя физику.

## Плашки вместо черноты

Страница, упавшая до первого кадра, — это результат. `record_scene` пишет
тёмный клип той же длины и рядом маркер `.missing`; монтаж рисует по маркеру
подпись. Повторная запись пропускает готовое (`--force` — перезаписать).

## Устойчивость пакетной записи

* каждый воркер — свой профиль Chrome в `/tmp`;
* два прохода на сцену: транзиентный сбой запуска Chrome не превращается в плашку;
* `Target.createTarget` + `attachToTarget`, а не навигация вкладки — вкладки
  не конфликтуют;
* готовность страницы — одно `awaitPromise`-выражение, а не поллинг из Python
  (поллинг по 0,1 с растягивал сцену до десятков секунд);
* после клипа рабочие кадры удаляются, пустой `_frames` убирается.

## Ограничения

* Chrome: `/Applications/Google Chrome.app` (не for Testing — тот лезет в
  связку ключей macOS). Linux: путь передаётся `--chrome`.
* macOS-arm собирает клипы комплектным ffmpeg из `video/bin` (`DYLD_LIBRARY_PATH`
  выставляется автоматически); на других ОС — любой `ffmpeg` в `PATH`.
* H.264 и `yuv420p` — совместимость важнее «идеального» цвета; для графики с
  резкими градиентами поднимайте `--crf` (например, 18) и проверяйте глазами.
* GitHub отклоняет файлы >100 МБ (`GH001`): сцены с шумным зерном нужно
  пережимать (CRF 28, 1080p) — см. историю `b6b0a0c` в репозитории.

## Проверка результата

1. `ffprobe`: длительность ровно `secs`, кадров ровно `secs × fps`.
2. Уникальных кадров больше одного — иначе сцена стояла; на статичных это
   ожидаемо, проверяйте по замыслу сцены.
3. Кадр на 1-й и последней секунде: объекты в кадре, нет чёрных/белых вспышек.
4. Прогон `--mode steps` на той же странице даёт сопоставимую картинку —
   значит, дело не в драйвере.
