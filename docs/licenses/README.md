# Реестр прав на внешние материалы

Одна JSON-запись на внешний материал: набор данных, документы, изображения,
код чужого harness. Наша лицензия на код адаптера не лицензирует автоматически
задачи, статьи, офисные файлы и credentials к сервисам. Лицензия harness не
лицензирует данные.

**Отсутствующая или непроверенная лицензия означает «не импортировать», а не
«считать MIT».** Это правило проверяется кодом (`dailybench holdout`), а не
памятью ревьюера.

## Формат

Схема — `$defs/material` в [`schema/holdout.schema.json`](../../schema/holdout.schema.json).
Имя файла равно `id` записи.

| Поле | Смысл |
|---|---|
| `schema` | `dailybench/license/1` |
| `id` | стабильный slug материала, он же имя файла |
| `origin` | URL источника материала (датасет, документ, репозиторий) |
| `revision` | закреплённая ревизия: тег, коммит, sha датасета |
| `upstream_id` | идентификатор материала у источника (`repo@rev:split`), дословно |
| `code_license` | SPDX-идентификатор лицензии кода |
| `data_license` | SPDX-идентификатор лицензии данных/документов/изображений |
| `attribution` | текст атрибуции, который уходит в bundle и публикацию |
| `redistribution` | `allowed`, `restricted`, `forbidden` |
| `status` | `verified`, `unverified`, `blocked` |

Допустимые значения лицензий — перечисление SPDX-идентификаторов в схеме.
`NOASSERTION` не принимается: он не даёт права на импорт. `null` тоже.

Необязательные поля: `adapter`, `recorded` (ISO-дата), `repository`, `note`,
`limitations`, `components` (разбор по частям: `name`, `role`, `license`,
`url`, `revision`, `split`, `version`, `note`). Разбор по частям не заменяет
поля верхнего уровня.

Запись пригодна к импорту при `status: verified` и `redistribution` не равном
`forbidden`: `restricted` проходит, но ограничение обязано быть названо в
`note`. `unverified` — запись уже есть, но права не прочитаны; `blocked` —
известное препятствие.

## Проверка

```bash
# весь реестр docs/licenses
.venv/bin/python -m dailybench licenses check

# отдельные записи или другой каталог
.venv/bin/python -m dailybench licenses check docs/licenses/bigcodebench.json
.venv/bin/python -m dailybench licenses check --dir path/to/registry
```

Коды выхода: `0` — все записи пригодны; `1` — есть ошибки схемы, отсутствующая
лицензия, неverified статус или `id`, не совпадающий с именем файла. Пустой
каталог — ошибка: потерянные записи не должны выглядеть как чистое состояние.

`prepare` официального адаптера вызывает `load_record_by_id` и отклоняет
импорт, если записи нет или она не пригодна. Проверка стоит в начале
`prepare`, до скачивания задач.

## Как заполнять

1. Прочитать LICENSE источника и карточку датасета; зафиксировать ревизию.
2. Записать отдельные `code_license` и `data_license` — обычно это разные
   файлы и разные права.
3. Внести `attribution` дословно из условия лицензии, включая требуемую форму.
4. Записать `limitations`: subset, локальный executor, что именно не покрывает
   лицензия.
5. Поставить `status: verified` только после шагов 1–4.

## Границы

- `bigcodebench.json` покрывает конкретный hard-subset и его scorer, а не
  библиотеки, которые импортируют задачи.
- Права на генератор и на сгенерированные им файлы — разные вещи.
- Проверка схемы не заменяет юридическую оценку: она ловит пропуск, а не
  неверно понятый текст лицензии.
- Credentials к внешним сервисам в реестр не входят: они не материал.
