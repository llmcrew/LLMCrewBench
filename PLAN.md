# План передачи: завершение свободного арт-блока и замечания ревью

## 1. Задача и согласованные решения

Пользователь первоначально попросил ревью репозитория и тестовых промптов. Затем попросил уменьшить ограничения арт-заданий, чтобы видеть собственные художественные решения модели: цвет, тональность и выразительность. После уточнения пользователь выбрал **одну свободную работу вместо 29 сюжетных заданий**.

Последний запрос: записать оставшуюся работу в Markdown для передачи другому агенту. Этот файл — план продолжения, а не заявление о завершённой реализации.

Обязательный согласованный результат для категории L:

- одна задача `L-1`;
- модель сама выбирает идею, сюжет, стиль, палитру, тональность и средства реализации;
- результат — самостоятельная HTML-страница, принимаемая общим механизмом доставки;
- HTML/CSS, SVG, Canvas и WebGL допустимы; Three.js не обязателен;
- не требовать `window.__probe`, `window.__step`, `window.__ready`, seed, воспроизводимость кадров, конкретные классы, материалы, объекты и параметры;
- статичная работа допустима, анимация необязательна;
- художественное качество оценивает человек по работе, а не автоматическая эвристика и не совпадение с golden;
- автоматическая проверка L — только техническая доставка/загрузка HTML и сохранение кадра;
- L не входит ни в 100-балльный рейтинг A–J, ни в численные баллы симуляций K;
- категория K сохраняет свой существующий физический контракт и проверки;
- чистый переход: удалить устаревшие тематические модули, тесты и потребителей; не создавать совместимые алиасы старого `ArtSpec`.

Замечания общего ревью перечислены отдельно от обязательного арт-перехода. Их исправление не было выполнено и не должно выдаваться за часть уже законченной работы. Если следующему агенту поручают также исправления ревью, использовать приоритеты разделов 5–8.

## 4. Правила работы с оставшимися замечаниями ревью

- P1 — нарушает корректность результата, останавливает общий прогон либо ломает границу доверия. P2 — ложный успех/штраф отдельного критерия, неточная диагностика или платформенная несовместимость.
- `наблюдалось` означает, что минимальный пример уже запускался в предыдущем ревью. Не повторять запуск только для подтверждения того же сообщения; использовать его как failing-before evidence, после исправления проверить changed path.
- `[INFERENCE]` — вывод по исходникам. До утверждения о runtime-дефекте нужен ограниченный безопасный repro.
- Исправлять причину, не подавлять исключения, не добавлять обход для конкретного seed/ответа и не переопределять плохое поведение как новое ожидаемое.
- Permanent tests — на поведение, границы, ошибки и переходы. Не тестировать исходный текст, точную формулировку prompt, forwarding/wiring и эхо mock.
- Параллельные исполнители могут владеть независимыми категориями. `core.py`, `runner.py`, `suite.py`, `browser.py`, `agent.py` и отчёты должны иметь одного интеграционного владельца.
- Запуски общего lint/test/selfcheck выполнять после интеграции, не у каждого исполнителя во время общей правки.

## 5. P1: целостность прогона, знаменатель и провенанс

### R1. Ошибки транспорта и evaluator не должны уменьшать знаменатель

**Файлы:** `dailybench/runner.py`, `dailybench/core.py`, `dailybench/report.py`, вызывающие evaluator-ы.

**Наблюдалось:** HTTP 503 записывается как `0/2`, а не явно непроверенный infrastructure result. Обратный дефект: I-1 с `top3=1` вызывает TypeError и выдаёт `0/0`; неверный ответ исчезает из знаменателя.

- [ ] Разделить wrong answer, ошибку/обрыв вызова модели, unavailable infrastructure и ошибку evaluator.
- [ ] Неверный/повреждённый ответ оценивается как неправильный с положенным `task.max_points`, а не `0/0`.

**Файлы:** `dailybench/browser.py:PIXEL_PROBE`, `dailybench/visual.py` HSV-distance/palette matching.

- [ ] `[INFERENCE]`: чёрный bucket попадает в допуск ярких тёплых цветов из-за слабого веса brightness. Проверить ахроматические/тёмные пробы до hue matching; исправление требуется для используемых K-предикатов, не для удаляемых художественных рецептов L.
- [ ] `[INFERENCE]`: регулярная выборка каждой четвёртой координаты при 1920×1080 может превратить 6.25% окрашенной площади в 100% sampled share. Проверить фазовое смещение и тонкие узоры; выбрать устойчивую выборку/агрегацию без зависимости от одного alignment.
- [ ] Не возвращать эти метрики в качестве оценок художественного качества L.

**Приёмка:** чёрный фон не заменяет требуемые яркие элементы; оценка площади не меняется радикально от сдвига узора на пиксель.

### V6. P2: отличать невозможность запуска Chromium от ошибки страницы

**Файлы:** `dailybench/browser.py:availability/render`, `dailybench/visual.py`, `dailybench/art.py`.

**`[INFERENCE]`:** каталог chromium может существовать без нужного executable; launch failure сейчас сводится к `ok=False` и выглядит как ноль модели.

- [ ] Проверять фактическую возможность запуска/тип инфраструктурного сбоя.
- [ ] Broken browser infrastructure — явно unverified/error, а не обычный wrong-page verdict.
- [ ] Проверить Windows-path изменение из раздела 2, старый каталог другой версии и отсутствующий executable.

**Приёмка:** поломка стенда не приписывается работе модели; ошибка JavaScript кандидата остаётся ошибкой кандидата.

### V7. P2: K должен соблюдать собственный API-контракт

**Файл:** `dailybench/visual.py:evaluate`.

**`[INFERENCE]`:** html-check K смотрит rendering/external, но не `probe_ok`; страница без обязательного `__probe` может получить html pass.

- [ ] Для K требовать действующий протокол, сохраняя кадр для диагностики при его нарушении.
- [ ] Для L не переносить это требование обратно.

**Приёмка:** переименование/удаление K `__probe` проваливает нужный технический criterion, но не теряет снимок.

### V8. P2: противоречивая камера K-1

**Файл:** `dailybench/tasks/visual_projectiles.py`, `PROBE_FIELDS` и `CAMERA`.

**`[INFERENCE]`:** схема probe объявляет `[0,6,14]`, а prompt, golden и evaluator используют `(0,7,16)`.

- [ ] Формировать схему возвращаемого camera из того же источника, что prompt/oracle.
- [ ] Проверить буквальный model answer по объявленной схеме и правильный golden.

**Приёмка:** в prompt, probe schema и evaluator одно согласованное положение камеры.

### Находки старого L, которые НЕ нужно чинить отдельно

После удаления 29 сценариев становятся неактуальными:

- несогласованные координаты/движение солнца старого L-1;
- разные коэффициенты sky-gradient старого L-2;
- несовпадение маршрута камеры старого L-29;
- старый motion-check на разных временных интервалах;
- atmosphere movement score по изменению JSON, а не изображения;
- отключение требования same-frame при отсутствующем `t`.

Закрывать их удалением obsolete L-кода и рецептов, не тратить работу на исправление удаляемых fixtures. Старый дефект cache hit без PNG уже частично устранён новой реализацией, но нужна реальная проверка boundary из A5.

## 9. Рекомендуемый порядок и распределение

1. **Один интеграционный владелец:** A1–A6. Сначала привести текущий несовместимый арт-переход в законченный вид.
2. **Общие результаты и провенанс:** R1–R4. Они влияют на достоверность любых остальных проверок и отчётов.
3. **Trust boundary выполнения:** C1/C4 и V1–V3. Не публиковать недоверенный live HTML без явной границы доверия.
4. **Независимые категории:** A/B/D/E/F/G/H/I, coding extraction/SQL и J contract после согласования общих интерфейсов.
5. **Корректность K:** V4–V8.
6. **Финальная интеграция:** все необходимые callsites, тесты, docs и provenance; fresh snapshot без переписывания старых результатов.

Для параллельной работы подходят отдельные владения:

- `tasks/instruction.py` + reasoning/longctx generators;
- `tasks/tools.py` и его trace criteria;
- F/G/H/I evaluator-ы и публичный dialogue/export по согласованному интерфейсу;
- coding/review trust boundary — один владелец общего решения;
- browser/publication security — один владелец с контрактом интеграции отчёта.

Не давать нескольким исполнителям одновременно менять `core.py`, `suite.py`, `runner.py`, `agent.py` и report API. Не ограничиваться отдельными passed tests до интеграции.

## 10. Общая проверка и критерии завершения

### Минимальные проверки после интеграции

```text
python -m dailybench selfcheck --only A,B,D,E,F,G,H,I,J
python -m dailybench selfcheck --only C
python -m dailybench selfcheck --only L
python -m pytest
```

Для K — существующие browser/render проверки и реальный запуск representative scenario. Для всех категорий full selfcheck зависит от доступности Chromium/Go/SQL backend; недоступное окружение документировать как недоступное, не превращать в passed.

Дополнительно:

- [ ] Smoke resume с совместимым и несовместимым run contract.
- [ ] Проверка fingerprint при изменении dialogue/workspace/tools и при одинаковой повторной генерации.
- [ ] Проверка transport failures, evaluator failures и malformed answers без улучшения знаменателя.
- [ ] Boundary cases генераторов плюс ограниченный детерминированный набор разных seed; не считать один стандартный seed доказательством всех допустимых draws.
- [ ] Честный правильный ответ, честный неверный ответ и безопасный adversarial case для каждого изменённого критерия.
- [ ] Реальный HTML report в браузере: снимки, live L, K, ошибки, skipped, две модели, isolated parent/opener.
- [ ] Актуальные README и docs описывают наблюдённое поведение, а не ожидаемый проектный результат.

### Definition of done

- Новая L-задача зарегистрирована и реально пройдена; старая тематическая система удалена.
- В L нет скрытых художественных рецептов, обязательных методов сцены и автоматических баллов за вкус.
- A–J по-прежнему дают установленный общий вес 100; K учитывается отдельно; L не добавляет художественные проценты/баллы.
- Записанный artefact, оцененный artefact и показываемый artefact совпадают по источнику.
- Resume не смешивает модели/контракты; fingerprint различает реальные задачи.
- Повреждённый ответ не может убрать задание из знаменателя; поломка инфраструктуры не маскируется под содержательный провал модели.
- Недоверенный код не подменяет авторитетный результат grader и не получает доступ к trusted report через parent/opener.
- У каждого закрытого замечания есть exercised evidence; `[INFERENCE]` не переименован в подтверждённое без запуска.
- Непроверенные или не взятые в работу замечания перечислены отдельно, без заявления «всё исправлено».
