# Запись живых веб-сцен в видео: фреймворк и практики

Набор для второго применения: снять исполняющуюся веб-страницу в клип
фиксированной длины так, чтобы клип честно показывал то, что видит зритель, и
не терял движение между кадрами. Вырос из записи витрины DailyBench
(`video/tools/`), но от бенчмарка не зависит.

## Что здесь есть

| Файл | Назначение |
|---|---|
| `timing.py` | Политика: окно 20 с в ходе 23 с, мастер 120 к/с при показе 60 к/с, занавес 0,75 с, словарь статусов, правила result-notes и таймлайна. |
| `layout.py` | Геометрия полос 2 × 960 × 1080, выезд полосы на весь кадр и проверка раскадровки. |
| `record_scene.py` | Запись одной сцены: headless-Chrome, CDP, покадровый PNG, h264, паспорт съёмки. Два режима: драйвер сцены и внешняя раскадровка `__step`; `--source-root`/`--repairs`. |
| `record_batch.py` | Пакетная запись дерева `<model>/pages/<scene>.html`, пропуск уже записанного, плашки вместо упавших страниц, `--repairs`, `--manifest`. |
| `page-driver.js` | Драйвер страницы: замер окна движения, развёртка на показ, `seek(n)` для записи, сетка и занавес (`dbstage`), клавиши/сообщения. |
| `curtain.js` | Чистая раскадровка занавеса: те же числа, что в `layout.py`; проверяется сравнением. |
| `manifest.py` | Манифест записи: уникальные пары, статусы, причины, result-notes, поиск исходника с приоритетом починки. |
| `verify_clips.py` | Проверка клипов (API и CLI): декод, PTS, кадры, SHA, чёрные кадры, уникальность, паспорт съёмки и quality-отчёт. |

Быстрый старт:

```bash
python3 record_scene.py https://host/scene.html out/scene.mp4
python3 record_batch.py pages/ clips/ 4 23 20 0.6 --manifest clips.json
python3 verify_clips.py clips --manifest clips.json
```

## Главная идея: не записывать реальное время

Записывать «как идёт» (по таймеру, `every N ms - screenshot`) - тупик: рендер
кадра сам занимает время, шаги сцены проскакивают, клип дёргается, а скорость
записи зависит от машины. Здесь наоборот: **кадры снимаются по одному и
сцена двигается ровно на один шаг на кадр**.

* Штатный путь - драйвер (`page-driver.js`). Он замеряет, сколько шагов
  подряд canvas реально меняется, и разворачивает это окно на клип.
* Путь без драйвера - `--mode steps`: фреймворк сам зовёт `window.__step(dt)`
  (один кадр - один шаг) и `window.__probe()`, если он есть.
* Клип всегда ровно `secs × fps` кадров; ни один шаг сцены не теряется.
  Частота - параметр: снимайте с запасом над частотой показа, если монтаж
  будет ускорять или замедлять клип; запас стоит и размера, и времени записи.

## Контракт съёмки

Значения по умолчанию - политика витрины, все они параметры:

| Параметр | По умолчанию | Смысл |
|---|---|---|
| `--secs` | `23` | длина записи: целое число ходов (23 с каждый) |
| `--open` | `20` | окно показа хода: 20 секунд контракта |
| `--fps` | `120` | мастер: частота съёмки и записи |
| `--display-fps` | `60` | показ; обязан делить мастер (или быть его кратным) |
| `--lanes` | `2` | полосы кадра; `1` - одиночная сцена без сетки |
| `--width/--height` | `1920×1080` | кадр; ширина делится на полосы (2 × 960) |
| `--curtain` | `0.75` | выезд полосы на весь кадр; ровно половина лида |
| `--lead` | `1.5` | пауза вокруг окна показа |

Запись состоит из целых ходов: 0,75 с занавеса, 20 с окна, 0,75 с возврата.
Поэтому `--secs` по умолчанию 23 с, а одиночная сцена без полос снимает один
ход. `timing.validate_timing` не даёт развести эти числа: занавес не половина
лида, показ не делит мастер, длительность не кратна ходу или кадру - отказ до
запуска Chrome. `Options()` проверяет то же при создании.

## Сетка и занавес

`--lanes 2` отдаёт драйверу `?dbstage=1&lanes=2&...`: страница становится
кадром из двух iframe-полос, каждая со своим драйвером. Внешний драйвер
раскладывает полосы по раскадровке `curtain.js` - на своём ходу полоса
выезжает на весь кадр за 0,75 с, стоит окно показа и уходит обратно. Порядок ходов
(`order`) и раскадровку считает `layout.storyboard`, поэтому кадр клипа
совпадает с кадром раскадровки, а монтаж получает готовые границы.

Раскадровка не зависит от монтажа: `layout.storyboard_errors` ловит
перекрытия, полосу вне диапазона и окно не той длины. Полосы без зазоров
накрывают кадр (960 + 960), это тоже проверяется.

## Исходники, починки и манифест

Имя исходника - `model/scene`. Режим `--repairs` ищет страницу сначала в
`_repairs`, потом в опубликованном дереве; исходник при этом не меняется, а
в паспорте остаётся `repaired`. `--manifest clips.json` ограничивает запись
парами манифеста (остальное - ошибка), а `verify_clips --manifest` сверяет с
ним клипы, маркеры и статусы: `ok` без клипа, плашка без маркера, маркер не
того статуса и дубли пар - провал проверки.

## Контракт страницы

Минимум, который понимает фреймворк:

```js
window.__ready = true;          // после первого кадра
window.__step = (dt) => {...};  // один детерминированный шаг
window.__probe = () => ({...}); // состояние, по желанию - и отрисовка
```

Правила, без которых запись врёт:

1. **Детерминизм**. Никакого `Math.random()` без seed и `Date.now()` в физике.
   Один и тот же шаг - один и тот же кадр.
2. **Рендер после шага, а не по таймеру**. Если страница рисует только в
   `__probe()`, драйвер перерисует сцену сам (оборачивает `WebGLRenderer`);
   без драйвера `record_scene` зовёт `__probe()` после каждого шага.
3. **Шаг не зависит от частоты кадров**. `dt` приходит аргументом; фиксировать
   его внутри страницы нельзя - клип и живой показ пойдут разным темпом.
4. **Один canvas - одна сцена** (или наоборот: если canvas несколько, сценой
   считается последний, а остальные скрываются; см. `apply_styles` в
   `video/tools/record_clip.py`).
5. **`preserveDrawingBuffer: true`** у WebGL-рендерера - иначе CDP-скриншот
   может снять пустой буфер.
6. **Без внешних запросов**: шрифты, картинки и three.js - локально; прокси и
   VPN в момент записи не должны влиять на кадр.

## Как устроен драйвер

```
__ready → замер (beat, подпись 64×48, QUIET=90 тихих шагов, потолок 1200)
        → кэш {freeze} в sessionStorage/window.name → reload
        → показ: seek(round(frame × freeze / span)), span = 4…10 с
        → пауза 0.9 с → reload (сцена начинается заново)
```

Запись вмешивается сообщением `pause` (автоплей стоит), забирает `freeze` и
вызывает `seek(round(k × freeze / (N−1)))`: первый кадр - начало окна, последний
- конец. `seek` назад не ходит, поэтому первый кадр гарантирует `seek(0)`.

У сетки (`dbstage`) окно равно длине клипа, поэтому рекордер ведёт кадр клипа
напрямую: `seek(k)` двигает и геометрию, и обе полосы. Полосы не делят окно
между собой - каждая идёт своим полным ходом.

Почему подпись 64×48 и сумма по всем canvas: дешёво (несколько миллисекунд),
устойчиво к сглаживанию и не ломается на страницах с двумя canvas, где первый -
WebGL без `preserveDrawingBuffer`.

## Темп: замедление - это нормально

Клип растягивает окно движения на всю длину. Множитель - `N / freeze`; для
окна 190 шагов это 7×, для 24 шагов - 57×, для одного шага - почти стоп-кадр.
Живой показ сжимает то же окно в 4-10 с, так что клип всегда медленнее.

Что с этим делать:

* не «ускорять» клип постфактум - режьте лишнее на монтаже;
* если сцена честно статична (терраин по условию, солвер сходится за шаг) -
  оставьте стоп-кадр, это правда о сцене, а не дефект записи;
* если стоп-кадр выглядит мёртвым - добавьте в сцену медленное движение
  (камера, пульсация света), не меняя физику.

## Плашки вместо черноты

Страница, упавшая до первого кадра, - это результат. `record_scene` пишет
тёмный клип той же длины, маркер `.missing` со статусом и причиной и паспорт
съёмки; монтаж рисует по маркеру подпись. Повторная запись пропускает готовое
(`--force` - перезаписать).

Статус - из словаря `timing.STATUSES`, а не свободная строка: `not_run`
(задачи нет в прогоне), `model_failed` (страница не доставлена или падает до
кадра), `capture_failed` (страница жива, запись сорвалась),
`evaluator_unavailable`, `skipped`, `media_missing`. Один `failed` на все
случаи смешивал «модель не справилась» и «сломался рекордер».

## Устойчивость пакетной записи

* каждый воркер - свой профиль Chrome в `/tmp`;
* два прохода на сцену: транзиентный сбой запуска Chrome не превращается в плашку;
* `Target.createTarget` + `attachToTarget`, а не навигация вкладки - вкладки
  не конфликтуют;
* готовность страницы - одно `awaitPromise`-выражение, а не поллинг из Python
  (поллинг по 0,1 с растягивал сцену до десятков секунд);
* после клипа рабочие кадры удаляются, пустой `_frames` убирается.

## Ограничения

* Chrome: `/Applications/Google Chrome.app` (не for Testing - тот лезет в
  связку ключей macOS). Linux: путь передаётся `--chrome`.
* macOS-arm собирает клипы комплектным ffmpeg из `video/bin` (`DYLD_LIBRARY_PATH`
  выставляется автоматически); на других ОС - любой `ffmpeg` в `PATH`.
* H.264 и `yuv420p` - совместимость важнее «идеального» цвета; для графики с
  резкими градиентами поднимайте `--crf` (например, 18) и проверяйте глазами.
* GitHub отклоняет файлы >100 МБ (`GH001`): сцены с шумным зерном нужно
  пережимать (CRF 28, 1080p) - см. историю `b6b0a0c` в репозитории.

## Проверка результата

`verify_clips.py` делает это без глаз и пишет `recording-quality.json`:

1. `ffprobe`: один поток, `h264`/`yuv420p`, размер кадра, частота, число
   кадров и длительность - ровно как в политике;
2. декод всех кадров: PTS обязан идти по `1/fps` без пропусков;
3. кадры пересчитаны по декодированной яркости: `ok`-клип не может быть
   целиком чёрным, плашка обязана быть чёрной, чёрные вставки замеряются;
4. SHA файла, уникальные миниатюры и самый длинный неизменный отрезок;
5. паспорт `.capture.json`: входной формат `png`, все кадры сняты, часы
   непрерывны, SHA исходника и `status` манифеста совпадают;
6. `--manifest` сверяет клипы, маркеры и статусы; дубли и неизвестные статусы
   - провал до декода.

Библиотечно проверка - `verify(path, Spec(), status=..., runner=...)`: `runner`
подменяет ffmpeg/ffprobe, поэтому логику можно прогнать на фейковых кадрах.

Глазами остаётся то, чего не видит метрика: кадр на 1-й и последней секунде и
сопоставимость `--mode steps` с драйвером.
