# Видео DailyBench-16

Ролик о бенчмарке: сравнение **DeepSeek-V4.1-Flash** и
**DeepSeek-V4.1-Flash 1017**, результаты, расходы и витрина исходных визуальных работ.
Записанный диктор и инструментальная музыка; длинная витрина K/L — только музыка.

Витрина строится по опубликованному сравнению
`reports/comparison-deepseek-1021/`; число живых клипов и плашек определяется
его исходными страницами и статусами, а отсутствующие работы не дорисовываются.

## Оформление и кадрирование

Стилистика первого ролика LLMCrew: крупные заголовки Inter, моноширинные
числа JetBrains Mono, тёмные плоские панели, тонкие линии, матрёшка и QR-коды.
В ролик перенесено оформление, не старый состав моделей или их результаты.

Вступление после приветствия собирается в две колонки: слева LLMCrewBench,
парные карточки конфигураций и показатели 2 / 100 / 49,
справа отдельная карточка GitHub с QR-кодом и читаемым адресом репозитория.
Карточки появляются через 1,2 секунды, общая длительность Intro — 24,8 секунды.

Сцена конфигураций (`Theory.tsx` → `Models`) сначала показывает показатели,
с 20,8-й секунды — скриншот файлов релиза 1017 на Hugging Face, затем с кадра
1291 — команду vLLM из `public/deepseek-v41-flash-uncensored-1017.sh`.
В текущем таймлайне Resolve команда видна с `01:01:48:34` до `01:01:56:03`;
JSON-аргументы оформлены в две колонки, комментариев в `.sh` нет.
Во всех состояниях снизу остаются логотип LLMCrew и QR-коды канала и чата из аутро.
Скриншот сохранён в `public/deepseek-v4.1-flash-1017-files.png`, иконка DeepSeek —
в `public/deepseek-icon.png`; источник иконки — [официальный сайт](https://www.deepseek.com/favicon.ico).
Оба изображения локальные: при показе и экспорте они не загружаются с внешних сайтов.

Блок Harness явно называет Pi: первые 19,15 секунды — схема цикла агента,
затем крупный предоставленный скриншот pi.dev из `public/pi-harness.png`.
Длительности подогнаны под запись, частота композиции остаётся 60 fps.

Витрина — две равные половины 960×1080 без внешних полей. Доступная работа
раскрывается до 1920×1080 на 20 секунд; движение шторы занимает по 0,75 секунды.
Неуспешная сторона остаётся в половине с причиной и не получает отдельного хода.
Один полноэкранный показ занимает 23 секунды с переходами; если нет ни одного,
обе половины остаются на 4 секунды. Общий таймлайн суммирует эти длительности.
Исправленный код не получает полноэкранного хода за исходный провал; расширенный
запуск без изменения HTML остаётся допустимым показом результата модели.
На экране нет служебных фраз про «живую сцену», fps и способ записи:
только название, модель и содержательные пояснения неудачи или ремонта.
Для отдалённых K-сцен `src/data/framing.json` хранит общую область видимого
результата по шести моментам клипа. Показ центрирует и увеличивает её не более
чем втрое; арт-сцены L используют центральное кадрирование без такой обрезки.
HTML, камера, материалы, освещение и мастер-MP4 при этом не изменяются.
После замены записей области можно пересчитать из корня репозитория:
`python video/tools/build_framing.py`.

## Что внутри

- Титр, разбор harness-цикла, сьют и категории, карточки двух конфигураций,
  сводная таблица результатов.
- Hero-сцена, затем **витрина**: 49 визуальных сцен (20 K + 29 L) подряд.
  Каждая сцена — две полноэкранные половины конфигураций; только доступные
  работы по очереди раскрываются шторой на 20 секунд и возвращаются.
- Полосы - **живые записи исполняющихся страниц** (не скриншоты): клипы снимаются
  с управляемыми часами в headless-Chromium, без привязки к реальному времени:
  1920×1080, H.264/yuv420p, 120 fps, 20 с (2400 кадров), CRF 16.
  Раскрытие переигрывает весь клип с начала без ускорения.
  Композиции и экспорт - 60 fps; исходные записи 120 fps не перекодируются.
- Для каждой пары модель/сцена статус различает `ok`, `skipped`, `not_run`,
  `model_failed`, `evaluator_unavailable`, `capture_failed` и `media_missing`.
  `not_run`/`skipped` не обвиняют модель; `model_failed` означает неуспех
  исходной работы, `evaluator_unavailable` - недоступного оценщика,
  `capture_failed` - инфраструктурный сбой записи, `media_missing` - клип,
  отсутствующий в поставке. Если HTML нет, новую сцену не дорисовывают.

## Команды

```bash
npm install
npm run preflight              # манифест, маркеры, ffprobe: ошибка до Studio/render
npm run studio                 # превью
npm run render -- --browser-executable "<chrome-path>"  # out/DailyBench-voiceover-final.mp4
npx remotion still scene-showcase out/frame.png --frame=300

python3 tools/preflight.py --no-decode       # согласованность без ffprobe
npm run timeline:resolve      # установить готовый монтаж в открытый проект flashVS1017
```

Запись запускается **из корня репозитория** в отдельный staging-каталог. Замени
`<chrome-path>` на путь к установленному Google Chrome; `--force` касается
только staging. Рядом со staged `clips/` создаются `clips.json` и
`showcase.json`:

```bash
python video/tools/record_all.py 4 20 0.6 --out video/out/recording-20s/clips --report-root reports/comparison-deepseek-1021 --chrome "<chrome-path>" --fps 120 --crf 16 --preset medium --startup-timeout 180 --force
python video/tools/verify_clips.py video/out/recording-20s/clips --manifest video/out/recording-20s/clips.json --output video/out/recording-20s/recording-quality.json
# код 1 у записи или провал verify - не заменять текущие клипы/манифесты
```

Проверка измеряет битрейт каждого файла и подтверждает длительность, параметры
потока, PTS и полный decode. Переключать набор можно только после успешной
проверки; затем `npm run preflight` проверяет уже опубликованный комплект.

Рендер на другой машине - `RENDER.md` (что переносить, требования, проверка).

## Как править

1. Монтаж — `src/data/edit.json`: `from`/`duration` в кадрах 60 fps,
   речевые источники и обрезки — в секундах, без изменения скорости.
   `cues` привязывают смену скриншотов и пояснений к речи. `motionRanges` задают
   интервалы реальной анимации; при добавлении движения их нужно обновлять,
   чтобы статический hold не заморозил новую анимацию.
2. Фактическая речь взята из проекта Resolve `flashVS1017`; исходные WAV скопированы
   в `public/audio/voice/`. `docs/voiceover.md` — сохранённый сценарный банк,
   не точный текст или тайминг текущей записи.
3. Статусы витрины (какая сцена, кто раскрывается) - `src/data/showcase.json`;
   пересобирается `tools/record_all.py` по маркерам и файлам, а не правится
   вручную. `clips.json` - производная проекция `${model}/${scene}/${status}`.
4. Отбор полноэкранных показов и их длительности — `src/video/showcase-timing.ts`;
   `showcase-data.ts` строит единый таймлайн для витрины и всей композиции.
   Проверки правил: `npm run test:showcase` (Node.js 22.18+).

Общий разбор подхода записи, грабли и чек-лист приёмки - `docs/recording/`
(фреймворк `record_scene.py`/`record_batch.py` и драйвер `page-driver.js`
вынесены отдельно и от ролика не зависят).

## Запись клипов: инварианты

- Клип снимается с **страницы решения** из
  `reports/comparison-deepseek-1021/_showcase/<модель>/pages/<сцена>.html`
  (отдаётся локальным http-сервером; `_vendor` рядом).
- Управляемые часы `record_clip.py` двигают `requestAnimationFrame`, таймеры
  или `window.__step(dt)` с шагом 1/120 с. `window.__probe()` вызывается после
  явного шага: у части страниц рендер выполняется в этом хуке.
- Записываются 20 секунд виртуального времени: 2400 кадров в 120 fps.
  Скорость рендера машины не приводит к пропускам шагов; штатная статичность
  исходной страницы не заменяется придуманным движением.
- Мастер-клип сохраняется целиком. Кадрирование и масштабирование отдалённых
  K-результатов выполняет только видеокомпозиция по `framing.json`; общий
  `videoFramingStyle` применяется и в шторах, и в Hero. Область объединяет
  содержимое нескольких моментов записи, чтобы камера показа не прыгала
  вслед за отдельным объектом. Яркость и графический код не исправляются.
- Статусная плашка объясняет причину: `not_run` - задачи нет в прогоне;
  `model_failed` - исходная работа не запустилась/упала;
  `evaluator_unavailable` - недоступен оценщик; `capture_failed` - страница
  жива, запись сорвалась. `result-notes.json` отдельно хранит причину и
  ожидаемый результат для частичного/неуспешного ответа.
- Изменённый код показывается отдельным клипом с пометкой «Технический ремонт ·
  не исходный результат модели». Увеличенное время ожидания без изменения HTML
  подписывается «Исходный код модели · расширенный запуск». Причина, правка
  или режим запуска и ожидаемый результат видимы; исторические баллы не
  заменяются, отсутствующая HTML-сцена не придумывается.
- Chrome и ffmpeg ищутся переносимо: сначала macOS-путь/video/bin, затем PATH;
  временные профили - `tempfile`, уборка - pathlib.
- Готовность по режиму: K - `__ready`/`__dbscene`, свободным L без хуков
  достаточно settled-разметки (документ догружен, разметка стабильна);
  `__ready` у L не требуется.

## Текущий ручной монтаж Resolve

Таймлайн **Flash vs 1017 — short K + vLLM — 60fps** сохраняет пользовательскую
нарезку: ранее удалённые куски не возвращены, оба разреза K-1 оставлены.
K-2–K-20 укорочены по действию каждого ответа: обычно около 7 секунд с раскрытием;
для завершившихся симуляций убраны неподвижные хвосты, статичные результаты
показаны коротко. Статичная поза K-19 не считается ошибкой: по контракту
обратная кинематика решается аналитически для фиксированной цели.

K занимает **4:07,5**, весь ролик — **25:10,3** (90 618 кадров, 60 fps).
Речь и её пользовательские разрезы сохранены; после K-1 убраны 950 кадров
цифровой тишины, оставшихся в звуке после видеонарезки. Между музыкой K и L —
трёхсекундный кроссфейд. Исходный пользовательский таймлайн сохранён отдельно.

- Видео: `out/DailyBench-vllm-shortK-final.mp4`.
- Таймлайн: `out/resolve/Flash-vs-1017-vllm-shortK-60fps.drt`.
- Проект: `out/resolve/flashVS1017-vllm-shortK-final.drp`.
- Точные исходные диапазоны и аудиосклейки: `out/edit/short-k/current-cut.json`.
- Резерв до изменений: `out/resolve/flashVS1017-user-cut-before-vllm-k.drp`.

DRT/DRP не содержат медиа. Для этого таймлайна сохраняй `out/edit/cache/`,
`out/showcase-master.mp4` и `out/edit/short-k/` с видеовставкой и WAV-фрагментами.
Для восстановления старых таймлайнов проекта также нужны их исходные записи.
`npm run render` и `npm run timeline:resolve` ниже собирают базовую композицию,
а не ручную нарезку Resolve; актуальная версия переносится через указанные DRT/DRP.

## Базовая композиция Remotion: речь, музыка и таймлайн

Базовая композиция длится **36:42,8** (132 168 кадров при 60 fps). Подводка к витрине
вынесена в отдельную сцену. Hero и все 49 сравнений K/L не содержат речи;
длинная витрина занимает **3:00,8–34:53,8**. Исторические цифры и окно 32К
на экране не меняются от увеличения дефолта будущих бенчмарков.

`npm run render` проверяет клипы, строит `public/audio/narration.wav`,
`music.wav`, `mix.m4a`, рендерит картинку и экспортирует:

- `out/DailyBench-voiceover-final.mp4` — готовый ролик с AAC и главами;
- `out/edit/timeline.json`, `timeline.csv`, `chapters.txt` — покадровый план и главы;
- `out/edit/music-credits.txt` — музыкальные кредиты для описания YouTube.

Для переноса проекта нужны и `public/clips/`, и `public/audio/`.
В `npm run studio` полный `DailyBench` воспроизводит готовый микс;
отдельные `scene-*` остаются визуальными композициями без аудио.

`npm run timeline:resolve` создаёт новый **60-fps** таймлайн с отдельными
V1 (сцены и 49 сравнений), A1 (диктор), A2 (музыка), маркерами и стартом
`01:00:00:00`. Исходный `Timeline 1` и его записи не заменяются.
Экспорты — `out/resolve/Flash-vs-1017-final-60fps.drt` и
`out/resolve/flashVS1017-final.drp`; резервная копия до монтажа лежит рядом.
DRT/DRP не встраивают медиа: таймлайн использует `out/edit/cache/`,
`out/showcase-master.mp4` и `public/audio/`. Не удаляй эти файлы после импорта;
при переносе нужны и проект, и эти медиа.

Музыка Scott Buckley: [Signal to Noise](https://www.scottbuckley.com.au/library/signal-to-noise/)
(вариант No Piano Melody) под речь,
[Electric Dreams](https://www.scottbuckley.com.au/library/electric-dreams/) под K,
[Reparateur](https://www.scottbuckley.com.au/library/reparateur/) под L.
Лицензия [CC BY 4.0](https://creativecommons.org/licenses/by/4.0/):
при публикации добавить кредиты в описание видео. Музыка приглушается под
диктором; музыкальные циклы склеены кроссфейдами, треки плавно сменяются,
в конце — трёхсекундное затухание.

Диктор собирается последовательной склейкой фрагментов и точных пауз, а не
миксом отложенных потоков: так FFmpeg не теряет речь после начальной тишины.
Длина каждого готового стема проверяется до замены файлов. В Windows перед
пересборкой аудио останови Studio: HTTP-сервер может держать `mix.m4a` открытым
даже после закрытия вкладки. После сборки запусти Studio снова.
Регрессия реального PCM (речь, паузы и длительность), из корня репозитория:
`python -m pytest tests/test_video_audio.py`.
